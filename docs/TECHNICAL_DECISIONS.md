# «Скинулись» — технические решения MVP

Статус: проектное решение для реализации и последующего принятия командой в репозитории. Дата: 11 октября 2026 года.

## 1. Источники и границы

Требования курса: https://github.com/andrey-limasov/app-conf/ (`project-requirements.md`, `definition-of-done.md` и опубликованные практики). Продуктовый контекст: `Skinulis_Project_Context.md` от 8 октября 2026 года.

Фиксируем выбранный пользователем продукт: Telegram-бот, подтверждение компенсации получателем, частичные компенсации, режимы `equal`, `custom`, `by_items`. Не добавлять OCR, мультивалютность, интеграцию с банками или веб-интерфейс.

Решения в этом документе являются техническим выбором проекта, а не новым обязательным требованием преподавателя. Команде нужно принять их PR и, где нужно, ADR.

## 2. Стек — один путь, без альтернатив в коде

- Python 3.12; FastAPI; Pydantic v2; pydantic-settings.
- SQLAlchemy 2.x **синхронный** `Session`, PostgreSQL 17, драйвер psycopg 3, Alembic. Не использовать `AsyncSession`.
- Для API: синхронные `def`-эндпоинты, короткая транзакция на операцию; создание/закрытие сессии на запрос. `Session` не передавать между запросами и потоками.
- Для бота: aiogram 3.x + httpx `AsyncClient`; только HTTP в API, без прямого доступа к БД.
- Установка зависимостей: uv, `pyproject.toml`, `uv.lock` в Git; фиксировать версии образов, не использовать `latest`.
- Денежный формат в БД: целочисленный `BIGINT` (`amount_kopecks`). На внешнем API — строго десятичные строки рублей с двумя знаками, например `"1500.00"`.
- JWT с конечным сроком; Argon2 через подходящую библиотеку хэширования; бот имеет отдельный внутренний service token и не запрашивает пароли в Telegram.
- Ruff для lint + format; mypy для статической проверки; pytest, pytest-cov, httpx, PostgreSQL service-container для integration.
- JSON-логи API/bot в stdout: стандартный `logging`, общий независимый модуль `skinulis_logging.py`, allowlist безопасных событий/полей; Docker logging driver с ограничением размера. T-10 использует явно разрешённый в постановке stdlib вместо ранее намеченного structlog: дополнительная зависимость не нужна, формат и privacy проверяются тестами. Не логировать токены, пароли, payload и сырые исключения.
- Docker Compose локально (`api`, `bot`, `db`); на VPS дополнительно Caddy reverse-proxy. Dockerfile non-root с кэшируемыми зависимостями и multi-stage при применимости.
- GitHub Flow, GitHub Actions: на PR `lint -> types -> tests (PostgreSQL) -> build`; после успешного merge `build -> push GHCR :SHA -> deploy SSH to VPS -> migrate -> healthcheck`. Не публиковать/деплоить недоверенные PR и не выдавать им production-секреты.

## 3. Архитектурные ограничения

Единый репозиторий, модульный монолит:

```text
app/
  main.py, config.py, db.py
  models/, schemas/, api/, services/, core/
bot/
  main.py, handlers/, keyboards/, api_client.py
alembic/
tests/unit/, tests/integration/
docs/adr/, docs/
.github/workflows/
AGENTS.md, pyproject.toml, uv.lock, compose.yaml, Dockerfile
```

`api/` выполняет ввод, вывод, аутентификацию и обработку ошибок; `services/` содержит всю бизнес-логику; `models/` — таблицы; расчёт долей и балансов — чистые функции на целых копейках. Из роутов и обработчиков бота запрещено копировать денежные алгоритмы. Не вводить Redis, Celery, Kafka, микросервисы, отдельный repository-слой повсюду, frontend или Kubernetes без отдельного ADR.

## 4. Идентификация и безопасность

Два законных способа обращения:
1. Внешний API: `/auth/register` (email + пароль), `/auth/login` (JWT). Извлечение пользователя только из проверенного токена. Все защищённые действия требуют аутентификацию и проверку членства.
2. Telegram: обработчик получает подтверждённый Telegram ID из update от Telegram, а **бот** (отдельный контейнер) вызывает API по внутренней сети с `BOT_SERVICE_TOKEN` и идентификатором отправителя. API принимает этот идентификатор только вместе с корректным service token. Не доверять `telegram_id`, полученному от произвольного внешнего клиента. В production внутренние служебные маршруты дополнительно закрываются reverse-proxy.

Первое обращение нового Telegram-пользователя: он выбирает «Создать профиль» — API создаёт Telegram-only учётную запись с уникальным `telegram_id`, без email/пароля. Для уже созданного API-аккаунта доступна привязка бота через криптографически случайный одноразовый токен, выпущенный в JWT-авторизованном API, с TTL 10 минут. Если Telegram ID уже привязан к другому аккаунту, связывание запрещено; слияние двух существующих аккаунтов не входит в MVP. Никаких паролей через бота.

Для `users` поля `email` и `password_hash` могут быть `NULL` только у Telegram-only аккаунта; `telegram_id` может быть `NULL` у API-only аккаунта; оба идентификатора нельзя оставлять пустыми одновременно. Уникальные индексы по заполненным email и telegram_id.

## 5. Транзакции и отказоустойчивость

- Все операции, изменяющие финансовое состояние группы (создание/изменение/soft-delete расхода, подтверждение компенсации), выполняются в одной DB-транзакции и берут `SELECT ... FOR UPDATE` блокировку строки `groups`. Во всех сервисах единый порядок взятия блокировок — сначала группа, затем операционные записи. Это сериализует конфликтующие записи в пределах группы, но не блокирует чтения.
- Создание расхода/компенсации принимает стабильный `client_request_id: UUID` от клиента. Уникальный индекс по `(group_id, client_request_id)` внутри таблицы предотвращает дублирование при повторной доставке Telegram updates/HTTP retries; повтор возвращает первоначальный результат или контролируемый `409` при несовпадающем теле.
- При `confirm` сначала блокировка группы, затем запись компенсации, затем повторная проверка текущих балансов. Подтверждение строго один раз; повтор возвращает текущий статус без повторного эффекта.
- `PUT expense` в транзакции полностью заменяет снимок долей и при необходимости позиции; на ошибке — rollback. `DELETE` реализуется через `deleted_at`, сохраняет историю, но исключает расход из балансов.
- Все балансы вычисляются запросом/сервисом из расходов и **подтверждённых** компенсаций, без дополнительного mutable-поля `balance` в users/groups.
- Миграции запускает отдельная одноразовая команда/job перед стартом API, а не каждый worker API. Ошибка миграций прерывает деплой.

## 6. Контракт данных и API

Использовать Pydantic discriminated union по `split_mode`: `equal`, `custom`, `by_items`. Режимы несовместимы по полям. Режим `by_items` **не** принимает отдельную общую сумму — сервер вычисляет её как сумму положительных позиций и возвращает в ответе; это упрощение ранее предложенного контракта.

В API суммы — строгие строки вида `"123.45"`, не float и не exponent notation. Ошибки одного формата: `{"error":{"code":"...","message":"...","request_id":"..."}}`. Валидационные ошибки отдавать HTTP 400 (переопределить стандартный 422), 401/403/404/409/500 по смыслу. Не раскрывать сведения о чужих группах; можно возвращать 404.

Минимальные публичные маршруты:
- `/auth/register`, `/auth/login`, `/users/me`, `/users/me/telegram-link-code`
- `POST /groups`, `GET /groups`, `GET /groups/{id}`, `POST /groups/{id}/invites`, `POST /group-invites/join`, `GET /groups/{id}/members`
- `POST /groups/{id}/expenses`, `GET /groups/{id}/expenses`, `GET /expenses/{id}`, `PUT /expenses/{id}`, `DELETE /expenses/{id}`
- `GET /groups/{id}/balances`, `GET /groups/{id}/settlement-plan`
- `POST /groups/{id}/settlements`, `GET /groups/{id}/settlements`, `POST /settlements/{id}/confirm`, `POST /settlements/{id}/reject`, `POST /settlements/{id}/cancel`
- `/`, `/health`, `/version`, `/docs`, `/redoc`.

Все списки с пагинацией, default limit = 20. Документация OpenAPI обязательна; публичные API-контракты меняются только вместе с тестами и обновлением клиента бота.

## 7. CI/CD и демонстрация

`ci.yml`: `pull_request` к `main`: uv sync --frozen, ruff check/format --check, mypy, pytest c PostgreSQL test DB + coverage >=60%, Docker build. Обязательный status check + 1 approval перед merge.

`deploy.yml`: только после слияния в защищённую main или ручной разрешённый запуск: build, push в GHCR с SHA, SSH на VPS, обновление Compose на опубликованный образ, однократная Alembic upgrade, безопасное обновление контейнеров, /health с проверкой БД и /version SHA. Не вводить секреты production в PR workflow. Одновременные деплои сериализовать (`concurrency`). Описать откат к предыдущему SHA (при несовместимых миграциях автоматический DB rollback не обещать).

Сервер: один VPS, Caddy (HTTPS), api, bot polling в одном экземпляре, db + named volume; PostgreSQL не публиковать наружу. Сборные логи через Docker, JSON и ротация. Проверка CI «красный тест блокирует merge» обязательна к демонстрации.

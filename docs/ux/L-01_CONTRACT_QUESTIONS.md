# L-01 — зависимости UX от API

Часть [Telegram UX](L-01_TELEGRAM_UX.md), Issue #4. Статус: вопросы для
человеческого ревью, **не новые контракты**. База `main`: `5c05ee6`, 26 октября 2026.
UX можно принять с явно отложенными зависимостями; реализацию зависимого действия
нельзя включать, пока не согласованы нужные OpenAPI-схемы и fixtures.

## 1. Что уже зафиксировано

Источники: [PRODUCT_RULES](../PRODUCT_RULES.md),
[TECHNICAL_DECISIONS](../TECHNICAL_DECISIONS.md),
[BOUNDARIES](../contracts/BOUNDARIES.md), [LERA_SPEC](../roles/LERA_SPEC.md).

| Область | Зафиксированное правило | Что из этого не следует |
|---|---|---|
| Actor | JWT либо проверенный bot-service запрос; Telegram ID берётся из Telegram update | Нельзя доверять произвольным author_id/payer_id/sender_id в публичном JSON |
| Онбординг | Telegram-only или одноразовая привязка; код действует 10 минут; без пароля в боте; merge запрещён | Полные служебные маршруты создания/проверки/потребления кода пока не заданы |
| Invite | Только владелец, TTL 24 часа, один раз, возможен отзыв; вступление добровольное | Нет согласованной схемы payload, отзывного маршрута и error.code для каждой причины |
| Деньги | API-строки с двумя знаками; equal/custom/by_items; сервер считает доли/итог/баланс/план | Предлагаемые поля O-01 не стали утверждённым OpenAPI |
| Предпросмотр | LERA_SPEC требует превью только от API | Нельзя придумать preview endpoint, сохранять временный расход или считать превью ботом |
| Компенсации | pending не влияет на баланс; confirm только получателю; reject получателю; cancel отправителю; terminal неизменяем | Нельзя считать timeout отказом, обещать отмену confirmed или локально менять баланс |
| Повторы | UUID client_request_id для создания расходов/компенсаций; повтор без дубля, конфликт тела — 409 | Не обещана та же схема для групп, join, link, PUT/DELETE и не задана вся семантика replay |
| Ошибки/списки | error.code/message/request_id; 400/401/403/404/409/5xx; limit 20 | Значения code, схемы страниц и точные success-коды ещё нужны |

## 3. Карта уже названных маршрутов

Только перечень из TECHNICAL_DECISIONS §6, для проверки границ.
Это не обещание работающего сервера, методов там, где они не указаны, или готовых схем.
Способ использования публичных маршрутов ботом согласуется с Тимуром отдельно.

| UX | Уже названо в TD | Что остаётся открытым |
|---|---|---|
| Профиль и код | `/users/me`, `/users/me/telegram-link-code`; `/auth/register`, `/auth/login` для самостоятельного API | Служебный bootstrap/link/read; публичный парольный вход не переносится в Telegram |
| Группы | `POST /groups`, `GET /groups`, `GET /groups/{id}`, `GET /groups/{id}/members` | Схемы, идентификация actor, повтор создания |
| Приглашения | `POST /groups/{id}/invites`, `POST /group-invites/join` | Deep-link, отзыв/чтение приглашений, точные причины отказа и повторы |
| Расходы | `POST /groups/{id}/expenses`, `GET /groups/{id}/expenses`, `GET /expenses/{id}`, `PUT /expenses/{id}`, `DELETE /expenses/{id}` | **Превью отсутствует в перечне**; схемы и конкурентное редактирование открыты |
| Балансы/план | `GET /groups/{id}/balances`, `GET /groups/{id}/settlement-plan` | Формат, порядок, нули, данные для выбора получателя |
| Компенсации | `POST /groups/{id}/settlements`, `GET /groups/{id}/settlements`, `POST /settlements/{id}/confirm`, `POST /settlements/{id}/reject`, `POST /settlements/{id}/cancel` | Нет названного GET одной записи; схемы списков и точные terminal responses ещё нужны |

## 4. Как зафиксировать согласование

Тимур проверяет onboarding/actor/приглашения, Олег — финансовый UX и схемы;
оба согласуют превью, конфликты и безопасные повторы вместе с Лерой.
Ответы записываются в командный issue/PR и принятые контракты с ссылкой на решение,
после чего актуализируются UX и fixtures в задаче реализации. L-01 не назначает
решение молча, не меняет чужие задачи и не вводит новые API-поля.

До человеческого решения нерешённая зависимость остаётся открытой, а сценарий
в чек-листе — будущим критерием проверки, не заявлением о работающей функции.

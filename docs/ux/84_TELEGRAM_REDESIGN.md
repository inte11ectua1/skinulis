## Аудит и композиция

Базовая версия: `fc9ac54cf59094c935d969fd85889cf16153eb97`.
Раньше названия `equal/custom/by_items`, `Участник #ID`, технические версии/номера и
раздельные сообщения с деталями заставляли сопоставлять интерфейс с API. Балансы
показывали знаки вместо смысла; частые повторные сообщения отодвигали актуальную
клавиатуру. Фильтры переводов занимали место на каждом экране.

Теперь: **заголовок → главная сумма/состояние → короткий контекст → действия**.
Безопасный HTML, жирные заголовки/отдельные суммы, единое форматирование `3 200 ₽`,
короткие inline-кнопки, один редактируемый экран. Используются реальные возможности
Bot API: произвольный RGB/CSS, Mini App и нарисованные Telegram-скриншоты отсутствуют.
Текст и кнопки длинных карточек разбиваются на страницы, данные не обрезаются;
подтверждение доступно после просмотра последней страницы. Список API по 20 записей.

| Экран | Новая структура / главное действие | Назад / пустое состояние |
|---|---|---|
| Старт | Польза сервиса; создать / привязать профиль | «Не сейчас», без записи до согласия |

Навигация: главное меню → группа → расходы / долги / план / переводы / участники.
Вторичные фильтры и полный чек открываются по запросу. После сохранения короткое
уведомление встроено в карточку; нет автоматической пачки баланс+план+детали.
Некоторые одноразовые уведомления и справка при активном вводе остаются отдельными
сообщениями: это сохраняет действующий черновик и его кнопки.

## Что стало проще

| Было (реальные прежние шаблоны) | Стало (реализованные шаблоны) | Эффект |
|---|---|---|
| `Участник #10`, `Участник #20` | `Антон`, `Саша · А`, `Саша · Б` | Люди вместо системных ключей |
| `equal / custom / by_items` | `Поровну / Указать суммы / По позициям` | Выбор понятен без API |
| `-1400.00 ₽ — участник должен` | `Антон · Нужно вернуть 1 400 ₽` | Не нужно интерпретировать минус |
| `pending / confirmed` | `Ожидает / Подтверждено` | Состояние и последствия названы явно |
| Новое сообщение после переключения участника | Изменение прежней карточки, «Выбрано: 2 из 3» | 0 новых сообщений на переключение |
| Детальный чек и балансы рядом с каждым результатом | Краткая карточка + отдельные подробности | Главное не теряется в истории |

[Светлый](84_PREVIEW.png) / [тёмный](84_PREVIEW_DARK.png) рендер четырёх карточек и [галерея реальных шаблонов](84_SCREENS.html) генерируется офлайн командой
`uv run python -m scripts.render_ux84`. Это **симуляция Telegram-представления**, не
скриншоты Telegram: настоящий Dispatcher/FSM/рендерер, фиктивные HTTP и Telegram
transports, синтетические имена/суммы. CSS галереи служит только для просмотра документа; стандартные стили показаны
условно, точные оттенки задаёт Telegram. На телефоне размеры/переносы зависят
от клиента Telegram. Галерея не заменяет ручную приёмку.

## Надёжность и границы

Каждый экран имеет новый opaque nonce; старая клавиатура отвечает alert без записи.
FSM, UUID, frozen request body, сверка текущего GET и запрет автоматических финансовых
повторов сохранены. `/cancel` не отменяет уже сохранённую запись. `/help` при активном
намерении не уничтожает его. Ошибка edit «сообщение удалено/не редактируется» допускает
одно новое сообщение; сетевой сбой не повторяет финансовую операцию.

Backend остаётся источником расчётов и прав. Бот только форматирует денежные строки,
не делит деньги. Hidden buttons не заменяют API author/member/receiver checks.
Имена и подписи не могут подменить actor. [Контракт display_name](../contracts/84_DISPLAY_NAMES.md).

## Ручная приёмка тремя аккаунтами

Только отдельный `@skinulis_testing_bot` и [локальный стек](../operations/LOCAL_TELEGRAM_UX.md).
Тестовые A, B, C; отдельная группа «UX-прогон», только вымышленные записи. Для confirm
в этой изолированной симуляции используйте синтетическую передачу, не реальные деньги.

1. Всем открыть /start: до согласия нет нового профиля; попробовать «Не сейчас».
2. Создать профили, проверить предложенные Telegram-имена без username.
3. Поменять имена; B и C временно назвать одинаково. Проверить метки и «вы».
4. Отдельно проверить привязку синтетического email-профиля одноразовым кодом;
   пароль/JWT не передавать боту. Привязка не меняет ручное имя и не сливает аккаунты.
5. A создаёт группу, B/C не видят её заранее.
6. A выдаёт две разные ссылки и приватно передаёт B/C. Каждый добровольно вступает.
7. Сверить имена/метки в участниках и на всех финансовых экранах.
8. A: «Поровну», `100.00` на троих. Проверить `33.34/33.33/33.33` в серверном preview;
   запись только после подтверждения. Удалить этот тест перед рестораном.
9. A: «Указать суммы», `10.00`, доли `0.00/3.33/6.67`; неверную сумму исправить.
   Удалить эту запись перед контрольным рестораном.
10. Чек: паста `700.00` для A; стейк `1100.00` для B; салат `500.00` для C;
    пицца `900.00` всем. Итого `3200.00`;
    доли `1000.00/1400.00/800.00`.
11. На выборе людей быстро переключать, выбрать всех/снять, попробовать пустое «Готово».
    Включая позицию чека: не появляются новые сообщения. Нажать старую кнопку.
12. До сохранения открыть подробности, вернуться, исправить позицию, получить новый preview.
13. После сохранения открыть карточку/список; балансы `+2200/-1400/-800`, план с именами.
14. B отмечает `500.00` A: «Ожидает», баланс прежний. A подтверждает:
    `+1700/-900/-800`. Двойное нажатие не меняет повторно.
15. Новую синтетическую запись A отклоняет; другую B отменяет. Баланс не меняется.
16. A изменяет расход, затем удаляет после предупреждения. Confirmed сохраняется:
    после удаления ресторанного расхода `-500/+500/0`.
17. B/C не видят invite-management и edit/delete чужого расхода; owner не правит чужой.
    Неполучатель не подтверждает запись.
18. На каждом шаге назад/отмена, /help и /start; нет случайного сохранения/потери
    неизвестного результата. Перезапуск тестового бота — только оператором после разрешения.
19. Локально отключить API (только оператор): понятная ошибка; вернуть локальный API,
    выполнить предложенный безопасный просмотр/повтор, проверить отсутствие дубля.
20. Оценить на телефоне: понятен ли текущий шаг, читаемы ли суммы/кнопки/длинные имена,
    удобно ли возвращаться, различимы ли pending/confirmed, нет ли визуального шума.

Владелец фиксирует PASS/FAIL и замечания по каждому пункту; согласие с внешним видом
и один живой прогон тремя аккаунтами обязательны до закрытия #84. Автотесты и галерея
подтверждают только техническую подготовку, а не субъективное качество интерфейса.

## Доработка после первого live-прогона владельца (тот же PR #85)

Владелец сообщил, что первый live-прогон показал заметное улучшение, но выявил
неодинаковые иконки и клавиатуры, остающиеся выше новых сообщений. Это обратная связь,
**не окончательная визуальная приёмка**. Следующий live-прогон новой доработки ожидается.

### Иконки и стандартные цвета

`bot/button_theme.py` — единая карта смыслов; `bot/keyboards.py` применяет её и к
обычным экранам, и к legacy read-only entrypoints. Иконки не являются правами или ID.

| Смысл | Иконка | Цвет по умолчанию |
|---|---|---|
| Главное меню / группы / профиль | 🏠 / 👥 / 👤 | Обычный |
| Создать группу / добавить расход | 🆕 / ➕ | primary, не больше одного на экране |
| Балансы / план / переводы | 💰 / 🧭 / 🔄 | Обычный |
| История / ожидающие | 📋 / ⏳ | Обычный |
| Предпросмотр / правка / удаление | 🔎 / ✏️ / 🗑 | primary / обычный / danger |
| Финальное подтверждение / отказ | ✅ / 🚫 | success / danger |
| Отметить внешний перевод | 💸 | primary |
| Назад / отмена / обновить / помощь | ↩️ / ❌ / 🔃 / ❓ | Обычный |
| Приглашение / фильтры | 🔗 / ⚙️ | primary (если другой primary ещё нет) / обычный |
| Поровну / точные доли / чек | ⚖️ / 🎯 / 🧾 | Обычный |
| Выбран / не выбран | ✅ / ☐ | Обычный, без дополнительной иконки |

В aiogram **3.31.0 из существующего lock** есть типизированное поле `style`:
используются только `primary`, `success`, `danger`. Нет extra kwargs или обновления
зависимостей. Отсутствие цвета не меняет смысл подписи, иконку или callback.
`colors=False` в общем рендерере проверяет вариант без стилей. Произвольный RGB/CSS
кнопкам не передаётся. Оттенки в реальном Telegram зависят от клиента и темы;
светлую/тёмную темы нужно проверить вручную. Custom emoji не используются.

Официальные источники: [Bot API / InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton),
[aiogram InlineKeyboardButton](https://docs.aiogram.dev/en/latest/api/types/inline_keyboard_button.html).
Custom emoji ограничены возможностями владельца/бота (Premium/Fragment); Unicode
обеспечивает базовую работу без платных требований.

### Жизненный цикл экрана

- Callback на текущей карточке редактирует её на месте.
- Новый текст/команда пользователя сначала снимает прежнюю клавиатуру и инвалидирует
  nonce. Ответная карточка отправляется **после** нового ввода, внизу истории.
  Это не попытка физически переместить старое сообщение.
- Повторный `/start` даёт максимум одну новую карточку на явную команду. Старые тексты
  сохраняются без кнопок; автоматической цепочки сообщений нет. Удаления истории нет.
- Успех создания профиля/группы, привязки, join и подтверждения отображается внутри
  следующей карточки. Выданная raw invite-ссылка остаётся отдельным приватным
  сообщением; её старое меню снимается, новое управление идёт после ссылки.
- `/help` при активном намерении показывает помощь с «Продолжить ввод» и «Отмена».
  Возврат создаёт свежие callbacks; UUID/body/версия и состояние операции сохраняются.
  `/groups`, `/profile`, `/start` при черновике напоминают продолжить или отменить,
  а не уничтожают ввод. Повторное предупреждение не накапливается в тексте.
- У уведомления о переводе больше нет отдельной клавиатуры, конкурирующей с текущей.
  Проверка идёт через командное меню и «Ожидают подтверждения».
- Ошибка редактирования: попытка снять прежнюю клавиатуру, затем одна новая карточка.
  Если связь не позволяет подтвердить снятие, конкурирующая карточка автоматически
  не отправляется. Финансовая операция автоматически не повторяется.
- `message is not modified` не запускает fallback. При уже удалённом/недоступном
  для редактирования сообщении Bot API может не позволить убрать старые кнопки;
  nonce всё равно недействителен. После потери MemoryStorage бот не может перечислить
  историю Telegram и массово почистить неизвестные сообщения. Нажатие исторической
  кнопки снимает её markup и даёт alert; свежая клавиатура другого сообщения сохраняется.
- В проекте используются inline-клавиатуры. Persistent ReplyKeyboardMarkup нет,
  поэтому лишнее сообщение с ReplyKeyboardRemove не добавляется.

### Встроенное меню и доступные возможности

Реальные обработчики `/start`, `/groups`, `/profile`, `/help`, `/cancel` описаны в
`bot/commands.py`. При следующем **разрешённом** старте тестового контейнера после
проверки `getMe.username == skinulis_testing_bot` вызываются `setMyCommands` (private
scope, русский и общий fallback) и `setChatMenuButton(MenuButtonCommands)`.
При другом username настройка запрещена до записи; при production-конфигурации этот
код не вызывается. Во время разработки внешних Telegram-запросов не выполнялось.
[Официальные методы](https://core.telegram.org/bots/api#setmycommands),
[командная кнопка](https://core.telegram.org/bots/api#setchatmenubutton).

Rich Messages присутствуют в актуальном Bot API и в установленной библиотеке, но
для этой доработки не вводятся: текущие HTML-карточки сохраняют совместимый единый
edit/fallback-путь. Поддержка rich-формата конкретными live-клиентами не проверена.
Изображения к каждому шагу не добавляются: они увеличили бы переписку/загрузку.
Mini App/WebApp нет. Bot API описывает ChatBackground как данные, но не даёт боту
метода автоматически менять обои личной переписки всех пользователей; фон выбирает
сам пользователь в клиенте. [Форматы сообщений](https://core.telegram.org/bots/features#messages),
[ChatBackground](https://core.telegram.org/bots/api#chatbackground).

### Повторная визуальная проверка

После отдельного разрешения на локальный перезапуск повторить прежний 20-шаговый
сценарий, дополнительно:

1. Светлая/тёмная тема: основные/опасные кнопки различимы, подписи понятны без цвета.
2. Создать группу и написать название: актуальная клавиатура находится **ниже** ввода,
   старая снята, отдельного «Группа создана» нет.
3. Меню рядом с полем ввода открывает пять работающих команд; в черновике переход
   не теряет данные, помощь возвращает к прежнему вводу, старый callback не сохраняет.
4. Быстро переключать участников: сообщение редактируется, без новых карточек.
5. Повторить /start, назад, неверное имя/сумму/код: одна актуальная клавиатура,
   предупреждения не растут повторениями, нет финансовых дублей.
6. После рестарта нажать старую кнопку: отказ; новые кнопки продолжают работать.

Перезапуск и применение командного меню ещё требуют разрешения владельца.


## Финальная доработка: ввод денег и состав строк (04.11.2026)

`bot/money_input.py` — единый парсер пользовательского ввода. Разбирает только
ASCII-цифры, целую часть без ведущих нулей и необязательные 1–2 цифры после точки
или запятой. Обычный/неразрывный/узкий неразрывный пробел допустим только с краёв;
табуляция, переносы и внутренние разделители запрещены. Строковая обработка
целых рублей/копеек дополняет дробную часть нулями, не округляет и не использует
float. `100`/`100,00`/`100.00` → `100.00`; `100,5`/`100.5` → `100.50`;
`0,01` → `0.01`; `12,34` → `12.34`. Ноль допустим лишь для custom-доли.
`100,999`, `-100`, `1e3`, `1 000`, `100руб`, `1,2,3`, пустая строка,
ведущие нули и неоднозначные разделители отклоняются. Длина wire-полей сохранена.

Парсер применяется к общей сумме equal/custom, каждой custom-доле, цене позиции,
правкам тех же полей и компенсации **до** замораживания HTTP body/UUID.
Wire DTO по-прежнему принимают только строгие строки с точкой и двумя знаками;
сервер рассчитывает preview/доли/сумму чека, проверяет лимиты и изменения долга.
Вывод уже использует единое правило: нулевые копейки скрыты, ненулевые — две цифры
(`100 ₽`, `100,50 ₽`, `1 250,75 ₽`). Никаких финансовых вычислений в клиенте.

`bot/keyboard_layout.py` составляет настоящие строки InlineKeyboardMarkup:

- Главное действие, подтверждение, второй важный баланс — отдельные строки.
- Соседние короткие вспомогательные действия — максимум два в ряд.
- Опасное действие — отдельная строка; рядом нет обычного/положительного действия.
- Навигация не объединяется с бизнес-действиями; короткие назад/отмена могут делить
  строку в исходном порядке. Порядок и callback-индексы сохранены.
- Длинные подписи, динамические группы/имена/записи и галочки участников остаются
  в одну колонку. Имена не сокращаются дополнительно ради сетки.
- Для фильтров направления и состояния отдельные группы пар; all/none — своя пара.
- Консервативная оценка длины учитывает широкие Unicode-символы. Это состав строк,
  **не фиксированная ширина/высота**: размеры и переносы выбирает Telegram-клиент.
- Иконки, primary/success/danger, права и opaque nonce не изменены; без цвета сетка
  та же. Выбор участников продолжает редактировать одну карточку.

Пример группы: прежде 8 одиночных строк; теперь основные «Добавить расход» и
«Кто кому должен» отдельно, «План переводов / Расходы» и «Переводы / Участники»
попарно, приглашение владельца и возврат отдельно. У обычного участника приглашения
по-прежнему нет. [Сравнение до/после](84_GRID_COMPARISON.png) и
[галерея](84_SCREENS.html) содержат четыре пары на одинаковых данных: главное меню,
группа, сохранённый расход и баланс. PNG — офлайн-симуляция, не Telegram.

Новые unit-тесты проверяют нормализацию/отказ, точность, строгость wire DTO,
компоновку/длинные имена/права, canonical body и повтор после timeout.
Реальный HTTP/PostgreSQL-прогон проверяет equal/custom, правку `100,5`, by_items
`0,01`, компенсацию `100,5`, нулевые доли и идентичный повтор запроса.
Существующие тесты финансов/конкурентности/старых callbacks не отключались.

### Дополнительная проверка на телефоне

1. На маленьком экране в светлой/тёмной теме проверить главное меню, группу,
   расходы, баланс, историю и подтверждение; подписи читаются и действия различимы.
2. Ввести `100`, `100,5`, `0,01` в расход/позицию/компенсацию; custom-долю `0,00`.
   Сверить preview и сохранённые копейки; `100,999` и `1 000` должны дать подсказку.
3. Правка суммы, отмена/назад, stale callback, повтор после timeout — без дублей.
4. Имена двух одноимённых участников различимы; галочки редактируют текущую карточку.
5. Owner видит приглашения, member — нет; удалить чужой расход нельзя.

Локальный polling/пользовательская база не перезапускались и не пересоздавались;
production/AWS/token не затрагивались. Безопасная последовательность пересборки
и отдельного разрешённого перезапуска — в [локальном runbook](../operations/LOCAL_TELEGRAM_UX.md#обновление-после-live-обратной-связи--без-потери-данных).

## 2. Общие правила интерфейса

- Сценарии ведутся в личном чате. В групповом чате: «Откройте личный чат с ботом,
  чтобы управлять расходами» и кнопка перехода; финансовые данные не выводятся.
- Команды: `/start` — вход/главное меню, `/cancel` — отмена незавершённого ввода,
  `/help` — «Создайте профиль, откройте группу и добавьте расход. Бот не переводит
  деньги. Для отмены ввода используйте /cancel». Кнопка `[Главное меню]` доступна
  на экранах просмотра; выход из мастера с данными требует выбора судьбы черновика.
- Меню `HOME`: «Что хотите сделать?» — `[Мои группы]`, `[Создать группу]`,
  `[Ожидают подтверждения]`, `[Профиль]`, `[Помощь]`. «Ожидают» открывает выбор
  группы, затем её входящие pending: общего межгруппового endpoint не предполагается.
  Профиль показывает только доступные данные текущего пользователя и тип привязки;
  перепривязки/слияния аккаунтов в меню нет.
- Карточка группы `GROUP`: `[Расходы]`, `[Добавить расход]`, `[Участники]`,
  `[Балансы]`, `[План переводов]`, `[Компенсации]`, `[К группам]`;
  `[Приглашения]` — только владельцу. API повторно проверяет права каждого действия.
- Один активный мастер на пользователя. Навигация не создаёт записи.
  `[Назад]` возвращает на предыдущий шаг и сохраняет введённые данные;
  изменение ввода делает прежнее превью и его кнопку подтверждения недействительными.
  Начало другого мастера: «Есть незавершённый ввод» — `[Продолжить]`,
  `[Отменить черновик и начать]`, `[Остаться здесь]`.
- На запросе `BUSY`: «Проверяю…» или «Сохраняю…»; повторный callback получает
  «Запрос уже выполняется». Кнопки записи временно недоступны. У каждого HTTP-запроса
  конечный timeout; его значение согласуется в клиенте, бесконечного ожидания нет.
- Доли, общий итог чека, балансы, допустимую компенсацию и план считает только API.
  Бот не суммирует custom-доли/позиции, не делит деньги, не вычисляет остаток или долг.
  Проверка суммы custom — серверная. Денежные значения передаются строками с двумя
  знаками после точки, без `float`/`round`. Бот может проверять форму ввода и хранить
  строки, а диапазоны и все финансовые проверки остаются на API.
- Подсказка суммы: «Введите рубли с двумя знаками после точки, например 1250.00».
  Не округлять, не исправлять запятую/экспоненту молча. Точная грамматика и
  нормализация названий — UQ-06; пока использовать однозначные примеры.
- Списки: запрашивать страницы по 20, показывать `[Назад по списку]`, `[Далее]`,
  `[Обновить]` по данным API. Отдельная кнопка `[К группе]` не меняет страницу.
  Страница, стабильная сортировка, признак продолжения — UQ-05; общего количества
  и количества страниц без ответа API не обещать. При изменившемся/опустевшем
  списке: «Список изменился. Обновите его»; `[Обновить]` возвращает к первой странице.

## 3. Сценарий A — первый запуск, профиль и привязка

**Вход:** личный `/start`, в том числе из приглашения. **Результат:** API подтвердил
создание/привязку профиля, затем `HOME` либо продолжение приглашения.
До согласия пользователя не создавать аккаунт и не вступать в группу.

```text
/start → проверка своего профиля → профиль найден → HOME
                            └→ новый → согласие → создать ИЛИ привязать → HOME
deep-link → сохранить намерение вступить → тот же onboarding → подтверждение вступления
```

| Состояние / вход | Сообщение и действия пользователя | Переход / результат |
|---|---|---|
| `START_CHECK`, `/start` | «Проверяю ваш профиль…» | Доверенный bot-service запрос (UQ-01); профиль найден → `HOME`; явно новый пользователь → `ONBOARD`; сбой не считать отсутствием профиля |
| `ONBOARD` | «Привет! Я „Скинулись“ — помогу учитывать общие расходы. Банковские переводы вы делаете сами. С вашего согласия свяжем Telegram с профилем сервиса. Пароль в боте не нужен. Если API-аккаунт уже есть, выберите привязку: объединять два профиля нельзя». `[Создать профиль]` / `[Привязать API-аккаунт]` / `[Не сейчас]` | Создать → `PROFILE_CONSENT`; привязать → `LINK_CONSENT`; отказ → завершить без записи |
| `PROFILE_CONSENT` | «Создать Telegram-only профиль, связанный с вашим Telegram? Email и пароль не нужны». `[Да, создать]` / `[Назад]` | Явное согласие → `PROFILE_SUBMIT`; назад → `ONBOARD` |
| `PROFILE_SUBMIT` | «Создаю профиль…» | Только подтверждённый API успех → «Профиль создан» → `HOME`; ошибки → §7 |
| `LINK_CONSENT` | «Связать этот Telegram с вашим существующим API-аккаунтом? Пароль сюда не отправляйте». `[Продолжить привязку]` / `[Назад]` | Согласие → `LINK_CODE` |
| `LINK_CODE` | «Получите одноразовый код через авторизованный API в операции /users/me/telegram-link-code. Он действует 10 минут. Пришлите только код. Не присылайте пароль, JWT или служебный токен». Ввод кода; `[Назад]`, `/cancel` | Потребление кода по UQ-01 → `LINK_SUBMIT`; назад → `LINK_CONSENT` |
| `LINK_SUBMIT` | «Проверяю код…» | Успех API → «Аккаунт привязан» → `HOME`; код не повторять в ответе/логах |
| `HOME`, повторный `/start` | «С возвращением! Что хотите сделать?» | Читается текущий профиль; нового пользователя не создавать |
| Любой мастер, повторный `/start` | «Есть незавершённый ввод». `[Продолжить]` / `[Отменить черновик и открыть меню]` | Сохранить текущий шаг или явно очистить; при запросе в пути → §7.3 |

Альтернативы и восстановление:

- Неверный, просроченный или использованный код: «Код недействителен или уже
  использован. Получите новый код в своём API-аккаунте и попробуйте снова» → `LINK_CODE`.
  Детализацию показывать только если её безопасно возвращает API (UQ-01).
- Telegram уже связан с другим аккаунтом / оба аккаунта использованы:
  «Привязать аккаунты нельзя: объединение профилей в MVP не поддерживается».
  `[Открыть мой профиль]` — повторная проверка текущей привязки, `[Главное меню]`
  только при подтверждённом профиле. Не предлагать обход через новый Telegram ID.
- Повтор создания/привязки и конфликт 409: проверить свой профиль; показать
  фактический результат, не утверждать успех по одному совпавшему коду ошибки.
- Timeout создания/привязки: «Ответ не получен. Сначала проверим, появился ли профиль».
  Проверка по UQ-01; повтор потребления кода/создания без согласованной семантики
  запрещён. Ошибка проверки → `[Проверить профиль]`, `[Помощь]`.
- 401, 5xx и недоступность API — §7; пароль не запрашивается при восстановлении.
  Если пользователь прислал пароль вместо кода, не цитировать/не логировать его;
  ответить «Нужен только одноразовый код, пароль сюда отправлять не нужно».

## 4. Сценарий B — группы и приглашения

**Вход:** `HOME → Мои группы / Создать группу` либо Telegram deep-link.
**Успех:** доступная участнику карточка группы или подтверждённое API вступление.
Лимит — 30 участников. Нельзя удалять группу/участника, передавать владельца
или принудительно добавлять пользователя; таких кнопок нет.

| Состояние / вход | Сообщение, кнопки и ввод | Переход / результат |
|---|---|---|
| `GROUPS`, `[Мои группы]` | «Ваши группы» + названия из API; кнопки групп, пагинация по §2 | Выбрать → проверить доступ → `GROUP`; пусто: «У вас пока нет групп» + `[Создать группу]`, подсказка попросить владельца прислать приглашение |
| `GROUP_NAME`, `[Создать группу]` | «Как назовём группу? Название — от 1 до 120 символов». Текст, `[Назад]`, `/cancel` | Допустимый ввод → `GROUP_REVIEW`; ошибка — повторить шаг без потери ввода |
| `GROUP_REVIEW` | «Создать группу „{название}“? Вы станете владельцем и первым участником». `[Создать]`, `[Изменить название]`, `[Отмена]` | Подтвердить → API → `GROUP`; 400/409/timeout → §7, UQ-02 |
| `MEMBERS`, `[Участники]` | «Участники „{группа}“» + имена, пометка владельца; пагинация, `[К группе]` | Только чтение; никаких кнопок удаления/назначения владельца |
| `INVITES`, владелец | «Одной ссылкой может воспользоваться один новый участник. Срок — 24 часа. Перешлите её тому, кого хотите пригласить». `[Создать приглашение]`, `[К группе]` | Явный запрос создания → API по UQ-02 |
| `INVITE_READY`, успех | «Приглашение создано. Действует 24 часа, используется один раз» + deep-link, доступный только владельцу | `[К группе]`; отзыв и его интерфейс — UQ-02, до контракта кнопку не включать |
| `INVITE_IN`, открытый deep-link | `/start` с непрозрачным payload по UQ-02; не показывать/не логировать payload | Неавторизован → §3, затем `JOIN_REVIEW`; авторизован → `JOIN_REVIEW`; ссылка сама не означает членство |
| `JOIN_REVIEW` | «Вступить в группу по этому приглашению?» `[Вступить]`, `[Не вступать]` | Имя группы до членства не раскрывать без разрешённого контракта; вступить → `JOIN_SUBMIT`; отказ очищает намерение и ведёт в `HOME` |
| `JOIN_SUBMIT` | «Проверяю приглашение…» | API атомарно проверяет ссылку и лимит; успех → «Вы вступили в группу» → `GROUP` |

Приглашение хранится только как краткоживущее намерение до явного вступления,
не как членство и не как финансовая запись. Если открыта другая ссылка/есть мастер,
сначала предложить продолжить мастер либо отменить его и открыть новое приглашение.
После перезапуска без намерения попросить снова открыть исходную ссылку.

| Альтернативная ветвь | Сообщение / восстановление |
|---|---|
| Просроченная ссылка | «Срок приглашения истёк. Попросите владельца прислать новую ссылку». `[Мои группы]` |
| Использованная ссылка | «Это приглашение уже использовано. Попросите новую ссылку». `[Мои группы]` |
| Отозванная ссылка | «Владелец отозвал приглашение. Попросите новую ссылку». `[Мои группы]` |
| Неверный/неизвестный payload | «Не удалось открыть приглашение. Проверьте ссылку или попросите новую». `[Главное меню]` |
| API не различает безопасно причины | «Приглашение недействительно или недоступно. Попросите владельца прислать новое». Не угадывать причину по HTTP-коду |
| Уже участник, повторный deep-link | Проверить свои группы; «Вы уже состоите в этой группе» → `GROUP` только при подтверждённом членстве. Потребляется ли токен — UQ-02 |
| В группе уже 30 человек | Если API подтверждает причину: «В группе уже 30 участников. Вступить сейчас нельзя». Не предлагать удалить участника; судьба токена — UQ-02 |
| Неучастник открывает старую кнопку группы/расхода | «Группа или запись недоступна» → `[Мои группы]`; при 403/404 не показывать название, участников, суммы |
| Участник пытается создать/отозвать приглашение | «Приглашать участников может только владелец» при доступной своей группе; API проверяет права независимо от кнопок |
| Timeout join/create/invite | Не создавать новую группу/ссылку повторным POST автоматически. Проверить доступные списки/состояние по UQ-02; если проверить невозможно, показать неопределённый результат по §7.3 |

Ссылка содержит секрет. В документе нет действующей ссылки; её точный payload,
сроки в ответе и доступное управление приглашениями не определяются этим UX.

## 5. Сценарий C — расходы

### 5.1. Общий вход и выбор участников

**Вход:** `[Добавить расход]` из группы либо выбор группы из списка.
**Успех:** API сохранил один расход, показана карточка с серверными долями.
Автор всегда плательщик, текущий проверенный пользователь; выбора чужого плательщика нет.
Плательщик может не входить в потребителей. Старые расходы не меняются при вступлении
нового участника; перечитывание списка участников не должно переписать исторический снимок.

```text
группа → название → режим → equal: сумма → участники ──────────────┐
                       ├→ custom: сумма → участники → точные доли ┤
                       └→ by_items: название/цена/участники позиций ┤
                              API-предпросмотр ←─────────────────┘
                                    → подтвердить → API-запись
                                    → исправить → новое превью
                                    → отменить → без записи
```

| Состояние | Сообщение / действие | Следующее состояние |
|---|---|---|
| `EXP_GROUP` | «Выберите группу для расхода»; доступные группы, пагинация, `/cancel` | Выбор/повторная проверка членства → `EXP_TITLE`; вход из карточки использует её группу |
| `EXP_TITLE` | «Как называется расход? От 1 до 120 символов»; текст | `EXP_MODE`; `[Назад]` → выбор группы; смена группы требует очистить зависимые данные после согласия |
| `EXP_MODE` | «Как разделить расход?» `[Поровну — equal]`, `[Точные суммы — custom]`, `[По позициям — by_items]` | Режим → соответствующий мастер; смена режима очищает несовместимый ввод после подтверждения |
| `EXP_AMOUNT` | «Вы оплатили расход. Введите общую сумму от 0.01 до 1000000.00 ₽» | equal → `EQ_MEMBERS`; custom → `CU_MEMBERS`; by_items сюда не попадает |

Выбор участников: «Кто участвует в расходе?» (или «Кто участвует в позиции?»),
список с `[✓ Имя]` / `[Имя]`, `[Выбрать всех]`, `[Готово]`, `[Назад]`, `/cancel`.
Исходно никто не выбран; повторное нажатие переключает выбор, дублей не создаёт.
Пустой выбор: «Выберите хотя бы одного участника» — остаться на шаге.
Добавлять можно только участников текущей группы; выбор себя не обязателен.
API повторно проверяет состав. Лимит 30 позволяет показать весь состав;
если ответ разбит на страницы, выбор сохраняется между ними.

### 5.2. Equal

| Состояние / действие | Сообщение / кнопки | Переход |
|---|---|---|
| `EQ_MEMBERS`, `[Готово]` | Показать выбранных; «Проверяю распределение на сервере…» | `EXP_PREVIEW_LOADING` по UQ-03 |
| `EXP_PREVIEW`, серверный ответ | «Предпросмотр. Группа: {группа}. Расход: {название}. Оплатили: вы. Режим: поровну. Всего: {итог API} ₽. Доли: {участники и доли API}. Расход ещё не сохранён». `[Подтвердить]`, `[Изменить сумму]`, `[Участники]`, `[Изменить название]`, `[Отмена]` | Подтвердить → `EXP_SAVE`; правка → нужный шаг и обязательное новое превью; отмена → §7.2 |
| `EXP_SAVE` | «Сохраняю расход…» | Успех → «Расход сохранён» + `EXP_DETAIL`; timeout/retry → §7.3 |

Копейки распределяет API по возрастанию user_id. Нулевые рассчитанные доли допустимы;
бот не заменяет их минимальным платежом и не пересортировывает получателей копейки.
Порядок отображения и точное представление нулей — UQ-06.

### 5.3. Custom

Вход после общей суммы → `CU_MEMBERS`. Выбранный непустой набор задаёт список ввода;
невыбранным участникам доли не придумываются.

| Состояние / действие | Сообщение / кнопки | Переход |
|---|---|---|
| `CU_MEMBERS`, `[Готово]` | «Укажите точную долю каждого выбранного участника. Нулевая доля 0.00 допустима» | `CU_SHARE` для первого выбранного |
| `CU_SHARE` | «Доля {имя}: введите сумму, например 400.00»; текст, `[Назад]`, `/cancel` | Сохранить строку для этого участника → следующий; после последнего → `CU_REVIEW_INPUT` |
| `CU_REVIEW_INPUT` | «Введённые доли: {имя → введённая строка}. Общая сумма расхода: {ввод}. Проверим точное совпадение на сервере». Кнопки участников для правки, `[Проверить]`, `[Изменить участников]`, `[Изменить общую сумму]` | Проверить → серверный предпросмотр UQ-03 |
| Сервер сообщает несовпадение | «Сумма долей должна точно совпасть с суммой расхода. Проверьте доли или общую сумму». Значение расхождения — только если вернул API | `CU_REVIEW_INPUT`; не прибавлять разницу последнему, не считать «осталось» локально |
| `EXP_PREVIEW`, успех | «Предпросмотр. {группа}, {название}. Оплатили: вы. Точные суммы. Всего: {итог API}. Доли: {данные API}. Сумма долей проверена сервером. Ещё не сохранено». `[Подтвердить]`, `[Изменить доли]`, `[Отмена]` | Сохранить → `EXP_SAVE`; правка → `CU_REVIEW_INPUT` |

Изменение набора участников сохраняет строки для оставшихся, удаляет исключённые,
запрашивает доли новых, затем заново проверяет весь запрос на API. Никакого
автоперераспределения. Ошибка API не стирает остальные введённые доли.

### 5.4. By items

Общая сумма отдельно **не вводится**, не вычисляется и не отправляется ботом.
На всём мастере есть название расхода и список позиций; максимум 50.
Стоимость/состав позиции и суммарный предел расхода проверяет API.

| Состояние / действие | Сообщение / кнопки | Переход |
|---|---|---|
| `ITEM_TITLE` | «Название позиции (1–120 символов). Чаевые и сервисный сбор добавляйте отдельными позициями»; текст | `ITEM_AMOUNT` |
| `ITEM_AMOUNT` | «Стоимость позиции, например 700.00. Введите фактическую положительную цену. Отрицательные скидки и возвраты не поддерживаются» | `ITEM_MEMBERS`; ошибка формата → тот же шаг |
| `ITEM_MEMBERS` | «Кто участвует в „{позиция}“?»; выбор по §5.1 | `[Готово]` → `ITEM_REVIEW`; `[Назад]` → цена |
| `ITEM_REVIEW` | «Позиция: {название}. Цена: {введённая строка}. Участники: {выбор}». `[Добавить в черновик]`, `[Исправить]`, `[Не добавлять позицию]` | Добавить → `RECEIPT_DRAFT`; отказ → список ранее добавленных позиций |
| `RECEIPT_DRAFT` | «В черновике {количество} позиций» + названия, введённые цены и участники без общего денежного итога. `[Добавить позицию]`, `[Изменить позицию]`, `[Убрать позицию]`, `[Предпросмотр чека]`, `[Отмена]` | Новая → `ITEM_TITLE`; правка → шаги позиции; убрать → подтверждение удаления из черновика; превью → API UQ-03 |
| 50 позиций | «Добавлено 50 позиций — это максимум. Можно изменить позиции или перейти к предпросмотру» | Добавление недоступно, правка/удаление/превью доступны |
| Пустой чек, запрос превью | «Добавьте хотя бы одну позицию» | `ITEM_TITLE`; API также не принимает пустой чек |
| `EXP_PREVIEW`, успех | «Предпросмотр чека. {группа}, {название}. Оплатили: вы. {позиции, их цены, участники и распределение API}. Итого: {общая сумма API} ₽. Итоговые доли: {снимок API}. Ещё не сохранено». `[Подтвердить]`, `[Изменить позиции]`, `[Изменить название]`, `[Отмена]` | Подтвердить → `EXP_SAVE`; изменить → черновик, затем новое превью |

Длинный чек выводится несколькими сообщениями/страницами в пределах Telegram;
единственная действующая кнопка подтверждения привязана к последнему полному превью.
Счётчики позиций — локальный UI, денежные итоги — только API. Суммирование итоговых
долей и распределений позиций ботом запрещено. Ошибка конкретной позиции возвращает
к ней по согласованной структуре ошибок UQ-04; без указателя поля дать выбрать позицию.
При превышении общего лимита: «API отклонил чек: превышен предел одного расхода
1000000.00 ₽. Измените позиции» — только при подтверждённой причине.

### 5.5. Предпросмотр, список, детали, редактирование и удаление

Предпросмотр всех режимов должен быть **без записи**. Нельзя создавать временный
финансовый расход ради превью и затем удалять его. Пока UQ-03 не согласован,
реальное подтверждение мастера заблокировано; в будущих mock-сценариях допускаются
только согласованные fixtures. API повторно валидирует запись при сохранении:
превью не резервирует состояние и не обещает неизменные будущие балансы.

| Состояние / вход | Сообщение / действия | Результат и альтернативы |
|---|---|---|
| `EXP_LIST`, `[Расходы]` | «Расходы группы» + название, сумма и плательщик из API; пагинация §2 | Пусто: «Расходов пока нет» + `[Добавить расход]`; выбор → `EXP_DETAIL` |
| `EXP_DETAIL` | «{название}. Оплатил: {плательщик}. Всего: {сумма}. Режим: {режим}. {доли API; позиции для by_items}». `[К расходам]`, `[Балансы]` | Только автору `[Редактировать]`, `[Удалить]`; владелец группы не получает права менять чужой расход |
| `EXP_EDIT`, автор | Перечитать текущую запись; «Редактируете свой расход. Изменение пересчитает балансы. Подтверждённые компенсации сохранятся; возможен обратный долг». `[Продолжить]`, `[Не менять]` | Мастер того же режима с историческим составом/данными; полный PUT и смена режима — UQ-07, не предполагать смену плательщика |
| `EXP_EDIT_PREVIEW` | Новое серверное превью + «Сохранить изменения? Подтверждённые переводы останутся в истории, балансы могут поменять знак». `[Сохранить изменения]`, `[Исправить]`, `[Отмена]` | Успех API → «Изменения сохранены»; перечитать детали/балансы. Ошибка → старый сохранённый расход остаётся исходным; черновик не выдавать за результат |
| `EXP_DELETE_REVIEW` | «Удалить ваш расход „{название}“ на {сумма} ₽ из расчётов? История сохранится. Подтверждённые компенсации не отменяются; возможен обратный долг». `[Да, удалить]`, `[Не удалять]` | Успех soft-delete → «Расход исключён из расчётов» + обновить список и балансы; отказ → детали |
| Устаревшие детали/404 | «Расход удалён или недоступен». `[Обновить расходы]` | Не показывать кэшированные финансовые данные как актуальные |
| Конкурентная правка/409 | «Данные изменились. Загрузите актуальный расход и проверьте изменения заново» | `[Открыть актуальный расход]`; прежний черновик не отправлять автоматически. Гарантия защиты от устаревшего PUT — только после UQ-07 |

Предупреждение о сохранении confirmed показывается перед **каждой** правкой/удалением,
так что оно действует и при наличии confirmed без предположения о поле-флаге в API.
После изменения баланс не корректируется локально и confirmed не откатываются.

## 6. Сценарий D — балансы, план и компенсации

**Вход:** карточка группы `[Балансы]`, `[План переводов]`, `[Компенсации]` или
уведомление о pending. **Успех:** показаны ответы API; денежный эффект возникает
только после подтверждения получателем. Бот не выполняет банковский перевод.

| Состояние / вход | Сообщение, кнопки | Переход / альтернатива |
|---|---|---|
| `BALANCES` | «Балансы группы. „Вам должны“ — положительный баланс; „Вы должны“ — отрицательный; ноль — расчёты закрыты» + участники и значения из API. `[План переводов]`, `[Обновить]`, `[К группе]` | Не пересчитывать сумму/знаки из расходов; представление нулей — UQ-06 |
| `PLAN` | «Рекомендуемые переводы по текущим балансам: {отправитель → получатель → сумма API}. План может измениться. Это рекомендация, минимальное число переводов не гарантируется». `[Я перевёл деньги]`, `[Обновить план]`, `[К группе]` | Пустой план: «По текущим данным переводы не требуются»; не обещать исчезновение pending |
| `SETTLEMENTS` | «Компенсации»; `[Входящие pending]`, `[Мои исходящие pending]`, `[История]`, `[Я перевёл деньги]`, `[К группе]` | Списки выбранной группы, пагинация §2; фильтры/схемы — UQ-08 |
| `ST_RECEIVER` | «Отметить уже выполненный внешний перевод. Кому вы перевели деньги?»; допустимые получатели по серверным данным, `[Назад]`, `/cancel` | Себя выбрать нельзя. Если нет допустимого долга: «Сейчас нет подходящего долга. Обновите балансы»; API решает допустимость |
| `ST_AMOUNT` | «Сколько вы фактически перевели {получатель}? Можно указать часть долга. Введите сумму, например 500.00. Текущие ограничения проверит сервер» | Строка → `ST_REVIEW`; не вычислять min/остаток; не применять потолок одного расхода к накопленной компенсации |
| `ST_REVIEW` | «Вы подтверждаете, что уже перевели {сумма} ₽ пользователю {получатель} вне бота? Будет создано ожидание подтверждения. Пока получатель не подтвердит получение, баланс не изменится». `[Да, я перевёл]`, `[Изменить сумму]`, `[Отмена]` | Подтверждение → `ST_SAVE` с одним `client_request_id` |
| `ST_SAVE`, успех | «Компенсация создана: pending — ожидает получателя. Баланс пока не изменился». `[Открыть запись]`, `[Компенсации]`, `[Балансы]` | API проверяет текущие балансы и участников; ошибки §7 |
| `ST_DETAIL`, pending | «{отправитель} → {получатель}, {сумма} ₽. pending — ожидает подтверждения. В балансах ещё не учтено» | Получателю `[Подтвердить получение]`, `[Отклонить]`; отправителю `[Отменить запись]`; `[Обновить]`, `[К компенсациям]` |
| `ST_CONFIRM_REVIEW`, получатель | «Подтверждайте только реально полученные деньги. Вы получили {сумма} ₽ от {отправитель}? После подтверждения запись нельзя отменить в MVP». `[Да, деньги получены]`, `[Назад]` | Confirm API → `confirmed`, обновить запись/балансы/план; 409 → ниже |
| `ST_REJECT_REVIEW`, получатель | «Отклонить запись? Если деньги не получены или сумма неверна, не подтверждайте её». `[Отклонить запись]`, `[Назад]` | Reject API → `rejected`; «Запись отклонена. Баланс не изменился» |
| `ST_CANCEL_REVIEW`, отправитель | «Отменить ожидание подтверждения? Это не возвращает деньги, переведённые вне бота». `[Отменить запись]`, `[Назад]` | Cancel API → `cancelled`; «Запись отменена. Баланс не изменился» |
| `ST_DETAIL`, terminal | «{confirmed — получатель подтвердил / rejected — получатель отклонил / cancelled — отправитель отменил}» | Нет кнопок изменения/удаления; `[Балансы]`, `[К компенсациям]` |

Если выбран перевод из плана, получатель и предложенная сумма показаны для проверки;
отправитель — только текущий пользователь. Частичную сумму он вводит сам.
Чужие рекомендации доступны только для чтения: отметить перевод за другого нельзя.
Не показывать вычисленный ботом «максимум»: только значение API, если контракт его
предусмотрит, иначе нейтральная подсказка с серверной валидацией.

```text
внешний перевод → sender создаёт pending (баланс прежний)
pending → receiver confirm → confirmed (API меняет баланс один раз)
        → receiver reject  → rejected  (без изменения баланса)
        → sender cancel    → cancelled (без изменения баланса)
        → confirm 409      → pending   (без изменения баланса)
terminal → повтор/старая кнопка → актуальный статус, без второго эффекта
```

Альтернативные ветви и восстановление:

- На confirm API заново проверяет балансы. При переплате/смене ролей и 409:
  «Балансы изменились. Подтверждение сейчас привело бы к переплате. Запись остаётся
  pending. Обновите балансы; получатель может отклонить запись, отправитель — отменить».
  `[Обновить запись]`, `[Балансы]`; не уменьшать сумму автоматически. Этот текст
  применим только к подтверждённой причине; общий 409 — §7.
- Pending не резервирует долг. При двух pending на весь неизменный долг нельзя
  обещать оба confirm; после первого успеха второй может получить 409 и остаться pending.
- Повторные confirm/reject/cancel и гонка получателя с отправителем: загрузить
  текущий статус, показать победивший переход. Точные success-коды и ответы на
  несовместимый terminal-переход — UQ-08/Q-07; второй финансовый эффект запрещён.
- При timeout confirm не писать «деньги не подтверждены» как факт: результат
  неопределён. Обновить запись по доступному списку и затем балансы. Не создавать
  новую компенсацию и не посылать другой переход ради восстановления.
- Уведомление получателю — best effort: «{отправитель} отметил перевод {сумма} ₽
  в группе {группа}. Подтвердите только реально полученные деньги» + `[Открыть запись]`.
  Перед показом деталей заново проверить actor/членство; callback не доказывает права.
  При недоставке запись остаётся во входящих через меню. Если отдельного чтения
  компенсации нет, открытие ищет запись в согласованном списке группы (UQ-08).
- Ошибочное confirmed нельзя тихо отменить/удалить: «В MVP подтверждённую запись
  изменить нельзя. Согласуйте дальнейшие действия с участником и командой проекта».
  Не создавать компенсирующий фиктивный перевод автоматически.

## 7. Сценарий E — ошибки, отмена и повторная доставка

**Вход:** любой запрос/мастер/старая кнопка. **Успех:** пользователь понимает,
сохранена ли запись, какой шаг повторить и где посмотреть фактическое состояние.
Черновик остаётся только локальным вводом; API — источник сохранённых данных.

### 7.1. Сообщения и восстановление

Точный `error.code` пока не утверждён (UQ-04). Не сопоставлять конкретную причину
по одному HTTP-статусу и не выводить сырой ответ/traceback. Если API безопасно вернул
`error.request_id`, добавить «Код обращения: {request_id}»; это не ключ идемпотентности.

| Ситуация | Текст бота | Состояние / восстановление |
|---|---|---|
| HTTP 400 | «Не удалось принять данные. Проверьте введённые значения» + безопасная конкретная подсказка при наличии | Сохранить черновик, вернуться к ошибочному шагу; без указателя поля показать список полей для правки |
| HTTP 401 | «Не удалось подтвердить доступ к сервису. Попробуйте проверить профиль позже. Пароль в Telegram не нужен» | Не создавать новый аккаунт. Проверить bot-service/auth по UQ-01; `[Проверить профиль]`, `[Помощь]`; не повторять запись до восстановления доступа |
| HTTP 403 | «Для этого действия недостаточно прав» | Скрыть недоступное действие, обновить доступный экран; без членства — общий текст недоступности |
| HTTP 404 | «Группа или запись недоступна» | `[Мои группы]` / обновить список; не раскрывать существование чужого объекта |
| HTTP 409 | «Состояние изменилось или запрос конфликтует с уже выполненным действием. Обновите данные» | Перечитать объект/список; применить специальную ветвь только по известной причине; не создавать новый UUID ради обхода конфликта |
| HTTP 500 и другие 5xx | «Сервис временно не смог обработать запрос. Попробуйте позже» | Чтение → `[Повторить загрузку]`; запись → сначала неопределённый результат §7.3; черновик сохранить |
| API недоступен / timeout | «Не удалось получить ответ сервиса» | Для чтения оставить экран с пометкой «Данные не обновлены» и `[Повторить загрузку]`; для записи «Результат пока неизвестен» и §7.3 |
| Некорректная форма суммы | «Введите сумму с двумя знаками после точки, например 1250.00. Округление не выполняется» | Тот же шаг; без молчаливого преобразования |
| Ноль/минус для расхода, позиции, компенсации | «Нужна положительная сумма от 0.01 ₽» по проверке API | Тот же шаг; custom-доля 0.00 — отдельный допустимый случай |
| Превышен лимит расхода | «Один расход — от 0.01 до 1000000.00 ₽. Измените сумму или позиции» по ответу API | Правка, затем новое превью; лимит не переносить на компенсацию |
| Название/состав/доли не приняты | «Проверьте название, участников и введённые суммы» + безопасное уточнение API | Правка без сброса прочих данных; не исправлять финансовую ошибку автоматически |
| Неожиданный код/невалидный ответ | «Получен непонятный ответ сервиса. Обновите данные или попробуйте позже» | Не считать успехом; запись → §7.3, чтение → повтор; без дампа ответа пользователю |
| Старая/чужая кнопка | «Эта кнопка больше не действует. Откройте актуальный экран» | Проверить пользователя и доступ; не применять callback к новому черновику |
| Текст там, где нужна кнопка | «Выберите действие кнопкой ниже или используйте /cancel» | Остаться на шаге; не интерпретировать текст как подтверждение |

### 7.2. /cancel и кнопка «Отмена»

| Где отмена | Поведение и сообщение | Конечное состояние |
|---|---|---|
| Нет активного ввода | «Сейчас нечего отменять» | `HOME` либо `ONBOARD`, если профиля нет |
| Onboarding до запроса | «Создание/привязка отменены. Для начала используйте /start» | Очистить код/намерение; профиль не создавать |
| Создание группы, любой расход, custom-доля, позиция, ввод компенсации до отправки | При наличии данных: «Отменить весь незавершённый ввод? Он не сохранится». `[Да, отменить ввод]`, `[Продолжить ввод]` | Да → очистить весь мастер и неиспользованный ключ → группа/меню; нет → прежний шаг |
| Только текущая позиция чека | `/cancel` отменяет весь расход с предупреждением выше. `[Не добавлять позицию]` отдельно отменяет только текущую позицию | Список уже введённых позиций сохраняется лишь при отказе от текущей позиции |
| Превью до подтверждения | «Отменить черновик? Расход ещё не сохранён»; те же кнопки | Да → исходная группа, без API-записи |
| Запрос записи уже отправлен | «Запрос уже отправлен. Отмена ввода не отменяет действие на сервере. Сначала проверим результат» | `RESULT_UNKNOWN` / ожидание текущего запроса; не обещать rollback и не посылать DELETE/cancel компенсации |
| Карточка существующей pending | `/cancel` — только навигация: «Незавершённого ввода нет. Для отмены записи используйте „Отменить запись“» | Запись остаётся pending; отдельное действие только отправителю по §6 |
| Confirmed/сохранённый расход | «Ввод не выполняется. Сохранённые записи этой командой не отменяются» | Просмотр записи/меню; не менять API |

### 7.3. Повторы, неизвестный результат и перезапуск

Для создания **расхода/компенсации** один `client_request_id` UUID относится к одной
подтверждённой операции в группе и внутри её типа. На первой отправке фиксируются
ключ и точное согласованное тело. Повтор Telegram update/двойное нажатие/HTTP retry
использует тот же ключ **и то же тело**. Не генерировать UUID на каждом нажатии;
не менять тело при retry. Финансовую идемпотентность обеспечивает API, не память FSM.
Семантика сравнения, replay после правки/удаления и права actor — UQ-09 / Q-06.

Пока результат неизвестен, отправленное содержимое нельзя редактировать или
подтверждать как новое намерение: доступны проверка результата и безопасный replay.
После достоверного отказа валидации без записи можно исправить данные, получить
новое превью и при новом подтверждении сформировать новый UUID для нового тела.
409 и timeout сами по себе не доказывают отсутствие записи; обходить их новым
ключом нельзя.

```text
PREVIEW → подтверждение → BUSY → известный успех → DETAIL
                            ├→ известная ошибка валидации → правка → новое превью
                            └→ timeout / 5xx → RESULT_UNKNOWN
RESULT_UNKNOWN → проверить API → найдено → DETAIL
               → безопасный retry исходного запроса с тем же UUID/телом
               → проверить нельзя → ждать/смотреть список, не создавать дубль
```

Сообщение `RESULT_UNKNOWN`: «Ответ не получен. Действие могло сохраниться.
Не создавайте его заново. Проверьте список или повторите исходный запрос».
`[Проверить результат]` — только доступным согласованным чтением;
`[Повторить исходный запрос]` доступна для финансового создания с прежним ключом/телом.
После replay показать возвращённый API результат и перечитать актуальную запись,
не предполагать, что она всё ещё в первоначальном статусе.

Создание группы/профиля/приглашения, join, PUT/DELETE и переходы компенсаций
не получают новую выдуманную гарантию `client_request_id`: применимость и чтение
результата — UQ-01/02/07/08/09. Неизвестный результат сначала проверяется по API;
без согласованного безопасного повтора не предлагать автоматический повтор записи.
Confirm/reject/cancel опираются на конечный автомат API и чтение текущего статуса.
При недоступном чтении: «Пока не удалось проверить результат. Попробуйте обновить
позже»; `[Обновить]`, `[Главное меню]`. Не объявлять неуспех и не менять состояние локально.

После перезапуска одного polling-процесса несохранённые черновики, намерения,
связь со старыми кнопками и ключи в FSM могут потеряться. На старый callback:
«Незавершённый ввод не найден — возможно, бот перезапустился. Начните заново.
Если уже нажимали подтверждение, сначала проверьте список: действие могло сохраниться».
`[Проверить расходы]` / `[Компенсации]` / `[Мои группы]` по доступному контексту.
На новом `/start` без памяти нельзя достоверно обнаружить потерю: показывать меню
и краткую подсказку «После перезапуска незавершённый ввод может потеряться.
Сохранённые записи остаются в сервисе». Не обещать восстановление UUID после рестарта;
при потерянном ключе запрещено автоматически создавать новую финансовую запись.
Для совершенно нового намерения пользователь заново вводит данные после проверки списка.

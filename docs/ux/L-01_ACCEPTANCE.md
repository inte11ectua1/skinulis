## 3. Будущая проверка реализации и ручной UX-прогон

Проверять на согласованных mock fixtures без live Telegram-токена, затем на sandbox
API в соответствующих задачах L-03–L-06. Наблюдать ответы API и записи, а не только
текст бота. Результаты финансовых примеров брать из PRODUCT_RULES/O-01 — бот
их отображает, не пересчитывает. Зависимый сценарий с незакрытым UQ отмечать blocked,
не подменять фиктивным успешным ответом или выдуманной схемой.

### A. Онбординг

- [ ] A-01: новый `/start` → согласие → Telegram-only → HOME; до согласия нет API-записи.
- [ ] A-02: существующий API-аккаунт → согласие → валидный одноразовый код → тот же аккаунт; пароль не запрошен.
- [ ] A-03: неверный/expired/used код → понятное сообщение и новый ввод; код не отражён в ответе/логах.
- [ ] A-04: Telegram уже привязан / merge запрещён → отказ без создания второго профиля; повторный `/start` не дублирует профиль.
- [ ] A-05: timeout/401 при проверке профиля не трактуется как новый пользователь; результат создания проверяется до повтора (UQ-01).
- [ ] A-06: `/start` в мастере предлагает продолжить/отменить; `/cancel` до отправки не создаёт профиль.

### B. Группы

- [ ] B-01: пустые и многостраничные «Мои группы»; создать → проверить → владелец первый участник; список участников доступен только своим.
- [ ] B-02: только владелец видит создание приглашения; обход кнопки всё равно отклоняет API.
- [ ] B-03: новый пользователь открывает deep-link → onboarding → явное «Вступить»; до вступления данные группы не раскрываются.
- [ ] B-04: 24-часовой TTL, однократное использование, отзыв: корректные тексты при различимых причинах API и общий текст иначе (UQ-02).
- [ ] B-05: повтор join уже участника, полная группа из 30, неверный payload, timeout и рестарт между onboarding/join обработаны без автоматического повторного POST.
- [ ] B-06: посторонний не читает группу/участников/расход; нет кнопок удаления группы/участника, передачи владельца или принудительного добавления.

### C. Расходы

- [ ] C-01: equal — группа/название/сумма/непустой уникальный состав → серверное превью → подтверждение/отмена. Плательщик может не быть потребителем.
- [ ] C-02: fixtures 100.00 на троих и 0.01 на троих: отображаются серверные доли, включая нули по принятой схеме; порядок кликов не распределяет копейки.
- [ ] C-03: custom — точная доля каждому; 0.00 допустима; несовпадение на 0.01 в любую сторону отклонено сервером без исправления последней доли.
- [ ] C-04: смена custom-состава запрашивает новых участников, убирает исключённых, сохраняет оставшиеся строки; после правки нужно новое превью.
- [ ] C-05: by_items — название чека, название/положительная цена/состав каждой позиции, следующая позиция; не запрашивается и не отправляется отдельный общий итог.
- [ ] C-06: пустой чек, 50/51-я позиция, пустой состав, нулевая/отрицательная позиция, превышение общего лимита, название 120/121 символ — верная ветвь без локального денежного расчёта.
- [ ] C-07: чаевые/сервис — отдельные положительные позиции; нет процентов/весов, отрицательных скидок, OCR, валют/банковских действий.
- [ ] C-08: длинный чек просматривается целиком; позиции можно править/убирать; актуальная кнопка подтверждения одна; отмена текущей позиции отличается от отмены всего расхода.
- [ ] C-09: превью API ничего не сохраняет; любая правка инвалидирует старое превью; без UQ-03 реальное сохранение не включается.
- [ ] C-10: список расходов — пусто/20/21/изменившаяся страница, детали всех режимов; назад возвращает к списку; вход извне снова проверяет доступ.
- [ ] C-11: только автор=плательщик редактирует/удаляет свой расход; владелец не правит чужой; после soft-delete обновлены список и серверные балансы.
- [ ] C-12: предупреждение перед PUT/DELETE при confirmed, возможен обратный долг; confirmed сохранены. Ошибка PUT не выдаётся за сохранённый черновик.
- [ ] C-13: новый участник не меняет исторические доли; устаревшая правка обрабатывается по UQ-07, без обещания несогласованного ETag/version.

### D. Балансы и компенсации

- [ ] D-01: «вам должны»/«вы должны»/ноль соответствуют API; план отображается в серверном порядке, пустой план понятен, глобальный минимум не обещан.
- [ ] D-02: sender отмечает только свой уже выполненный внешний перевод другому участнику; частичная сумма, слишком большая сумма и отсутствие допустимого долга проверяются API.
- [ ] D-03: создание pending не меняет баланс и не резервирует долг; потерянное уведомление не скрывает запись из меню входящих выбранной группы.
- [ ] D-04: получатель видит предупреждение «только реально полученные деньги» и отдельное подтверждение; после confirmed перечитываются запись, балансы, план.
- [ ] D-05: reject только получателю, cancel только sender и только pending; оба не меняют баланс; terminal не редактируются/не удаляются.
- [ ] D-06: повтор confirm, повтор reject/cancel, гонка confirm/cancel показывают актуальный terminal и не дают второго эффекта; точные ответы соответствуют UQ-08.
- [ ] D-07: две pending на полный неизменный долг → первый confirm успешен, второй 409/pending; изменившиеся расходы/смена ролей → повторная серверная проверка, без автоматического уменьшения суммы.
- [ ] D-08: ресторанный пример PRODUCT_RULES: pending Антон → Тимур 500.00 сохраняет +2200.00/−1400.00/−800.00; после confirmed API возвращает +1700.00/−900.00/−800.00. Повтор confirm не меняет результат.
- [ ] D-09: ошибочное confirmed не имеет кнопки отката; уведомление/старая кнопка не доказывают права; чужой пользователь получает отказ без раскрытия данных.

### E. Надёжность диалога

- [ ] E-01: отдельно смоделированы 400, 401, 403, 404, 409, 500, другой 5xx, timeout, недоступный API, невалидный ответ; нет зависания и выдачи сырого ответа.
- [ ] E-02: неверные суммы (запятая, экспонента, лишняя точность) не округляются; положительные суммы и нулевые custom-доли различаются; предел расхода не ограничивает накопленную компенсацию.
- [ ] E-03: `/cancel` до данных/на каждом поле/на превью/во время запроса/после сохранения действует по §7.2; не отменяет существующую pending случайно.
- [ ] E-04: двойной клик и повтор update при создании расхода/компенсации используют прежний UUID и точное тело; несовпавшее тело не повторяется с новым UUID ради обхода 409.
- [ ] E-05: timeout после фактического commit → неизвестный результат → чтение/replay исходного запроса → одна запись; не писать «не сохранено» без доказательства.
- [ ] E-06: рестарт до отправки теряет только черновик; после отправки потерянный UUID не порождает автоматический POST с новым ключом; сначала проверка сохранённых записей.
- [ ] E-07: старое превью, callback другого пользователя, отсутствующая FSM и неожиданный текст не подтверждают действие; отображается способ вернуться на актуальный экран.
- [ ] E-08: локальные состояния не хранят значимый финансовый результат; нет доступа бота к БД, секретов в логах, выдуманных URL/полей/гарантий API.

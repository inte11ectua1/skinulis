# M6: smoke и демонстрация трёх пользователей

Сценарий для **изолированной тестовой БД**, не production. Финансовые действия ниже
синтетические: банковские деньги не отправляются. Исполнен API smoke и offline
Telegram transport; **live Telegram не выполнялся и не разрешён**.
[Результаты](M6_ACCEPTANCE_REPORT.md), [инструкция пользователя](../USER_GUIDE.md).

## Подготовка и повторяемость

Тестовые персонажи: Тимур T (плательщик), Антон A, Даша D. В новой БД зарегистрировать
их в этом порядке; записать внутренние ID из профилей: **T < A < D**, не путать с
Telegram ID. Отдельный четвёртый профиль X используется только для проверки отказа
чужому пользователю, он не участник финансового сценария. Реальные имена/контакты
не нужны; для API использовать `timur@example.com`, `anton@example.com`,
`dasha@example.com`, случайные пароли в памяти и JWT без печати/скриншотов.

Для ручного чистого старта сначала по [README](../../README.md) подготовить **новый**
секретный env-файл 0600 вне Git; существующий `.env` не менять. Выбрать незанятый
loopback-порт, уникальное имя проекта и полный проверяемый SHA. Например:

```sh
export APP_COMMIT_SHA="$(git rev-parse HEAD)"
docker compose --env-file /absolute/private/m6.env -p skinulis-m6-demo -f compose.yaml config --quiet
docker compose --env-file /absolute/private/m6.env -p skinulis-m6-demo -f compose.yaml up --build -d
docker compose --env-file /absolute/private/m6.env -p skinulis-m6-demo -f compose.yaml ps -a
```

Env задаёт отдельные POSTGRES_DB/USER/PASSWORD, JWT_SECRET_KEY, BOT_SERVICE_TOKEN,
APP_ENV=test, API_PORT. `DATABASE_URL` для Compose не задаётся. Уникальный project
создаёт новый `postgres_data`, db не публикует порт, api привязан к 127.0.0.1.
Ни имя production project, ни production env/volume использовать нельзя.
Ожидать db healthy, migrate exited0 и API `/health` 200/database=ok; `/version`
должен совпасть с APP_COMMIT_SHA. Не выводить `compose config` без `--quiet`.

Авторизовать T/A/D через register → login; `/users/me` каждого возвращает именно
его ID, без JWT — 401. T создаёт **M6 Ресторан**, выпускает две разные ссылки,
A и D добровольно вступают. Проверить 3 участника. X получает 404 на группу;
A получает 403 при выдаче приглашения.

В offline Telegram варианте создать Telegram-only T, привязать API-профиль A
одноразовым кодом, создать D после открытия приглашения и явного согласия.
Бот показывает `Участник #ID`, а не имена. Не запускать `bot.main` или polling.

## Полный smoke (15–20 минут)

Все суммы в таблице — рубли, в порядке **T/A/D**; каждый баланс проверять на сумму 0.

| Шаг | Кто и действие | Ожидаемый результат |
|---|---|---|
| 1 | T: equal `100.00`, участники выбрать D/T/A | Сохранённые доли в порядке ID: `33.34 / 33.33 / 33.33`; балансы `66.66 / -33.33 / -33.33` |
| 2 | T: удалить этот расход, текущая expected_version | Soft-delete, баланс `0.00 / 0.00 / 0.00` |
| 3 | T: custom `10.00`, доли T=`0.00`, A=`3.33`, D=`6.67` | Нулевая доля сохранена; балансы `10.00 / -3.33 / -6.67` |
| 4 | T: удалить custom | Снова все нули |
| 5 | T: чек by_items по позициям ниже | Итог `3200.00`, доли `1000.00 / 1400.00 / 800.00` |
| 6 | Все: балансы и план | `2200.00 / -1400.00 / -800.00`; A→T `1400.00`, D→T `800.00` |
| 7 | A: синтетический перевод T `500.00`, pending | Баланс прежний; запись видна у получателя |
| 8 | D пытается confirm этого перевода | 403, запись остаётся pending |
| 9 | T: подтвердить и повторить то же подтверждение | confirmed ровно один раз; `1700.00 / -900.00 / -800.00` |
| 10 | A: новый pending `100.00`, T: reject | rejected; те же балансы |
| 11 | A: новый pending `100.00`, A: cancel | cancelled; те же балансы |
| 12 | A пробует править расход T | 403; owner тоже не может править чужой расход |
| 13 | T: заменить ресторан на equal `3000.00` для всех | version увеличена; confirmed500 сохранён; `1500.00 / -500.00 / -1000.00` |
| 14 | T: повторить PUT с прежней expected_version | 409, сохранённая новая версия не меняется |
| 15 | T: удалить новую версию | `-500.00 / 500.00 / 0.00`, обратный долг T→A500; confirmed не удалён |

Ресторанный чек (общую сумму by_items не вводить):

| Позиция | Цена | Потребители |
|---|---|---|
| Паста | `700.00` | T |
| Стейк | `1100.00` | A |
| Салат | `500.00` | D |
| Пицца | `900.00` | T, A, D |

В Telegram: карточка группы → **Добавить расход** → **По позициям — by_items** →
название → первая позиция → цена → участники → **Готово**, затем **Добавить позицию**.
После четырёх позиций — **Серверный предпросмотр**. До **Подтвердить расход** записи
нет. После подтверждения — «API подтвердил исходное создание расхода» / карточка сохранённого
расхода; сверять сумму и доли API, не локальный подсчёт клиента.

Компенсация: A **Я перевёл деньги** → участник T → `500.00` → **Да, я уже перевёл
деньги**; T **Ожидают подтверждения** → группа → **Открыть перевод #ID** →
**Подтвердить получение** → предупреждение «реально полученные деньги» → **Да,
деньги получены**. В тесте это имитация состояния, а не заявление о банковском переводе.
Не рассчитывать на уведомление: открыть меню получателя явно.

## Негативные сценарии и восстановление

| Проверка | Ожидаемое поведение / действия |
|---|---|
| equal `0.01` на троих | `0.01 / 0.00 / 0.00` по ID, сумма ровно копейка; отдельный тест, удалить до ресторана |
| custom с несовпадающей суммой / неверным полем actor | 400, записи нет; исправить и новый preview |
| Нет JWT / ложная service credential | 401; JWT не заменяет bot-service token |
| Чужой объект | 404, существование/состав группы не раскрывается |
| Не owner/автор/receiver | 403; нет повышения прав от владения группой |
| Повтор expense POST | Сохранить **тот же UUID и body**: replay200, одна запись. Новый title с тем же UUID →409 |
| Потерян ответ expense POST после commit | В mock-транспорте потерять только ответ, затем повторить исходный intent. Прочитать GET: исторический replay может отличаться от уже изменённого/удалённого current state |
| Потерян ответ settlement POST/transition | Перечитать список/карточку. Не создавать новый UUID; повтор того же действия не меняет баланс дважды |
| Два pending на полный долг, конкурентный confirm | Одно подтверждение, второй409/pending; независимые соединения, без финансового эффекта второго |
| Расход изменён перед confirm | `settlement_balance_conflict`409, pending сохраняется; отклонить/отменить, сумма сама не корректируется |
| Устаревшая версия PUT/DELETE | 409; заново прочитать карточку и подтвердить новое намерение |
| Timeout приглашения/привязки | Сначала профиль/группы/metadata; не выпускать новый секрет и не повторять linking вслепую |
| `/cancel`, stale-кнопка, перезапуск | Commit не отменяется; сначала проверить историю, новый ввод только после выяснения результата |

Timeout нельзя демонстрировать отключением production-сети: использовать готовые
изолированные tests с потерей ответа после настоящего commit. Тесты гонок используют
PostgreSQL17 и независимые соединения, не последовательные поддельные ответы.

production runbook к этому тесту или наоборот.

  профили можно подготовить заранее, но показать соответствие ID.

- **2:50–4:10:** синтетический pending500 не меняет баланс; получатель confirm,

- **4:10–5:00:** чужой actor403/404; удалить свой расход → обратный долг500,

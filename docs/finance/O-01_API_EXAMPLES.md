# O-01 — предлагаемые примеры входных данных API

**Предлагаемый контракт для согласования, не действующий OpenAPI.** Маршруты и discriminated union предусмотрены [TECHNICAL_DECISIONS §6](../TECHNICAL_DECISIONS.md); полные схемы и имена полей пока не реализованы. Числовые ID ниже — синтетические. Типы ID, поля, success-коды, error.code и повторы требуют [Q-01/Q-02/Q-06/Q-07/Q-08](O-01_OPEN_QUESTIONS.md).

Правила и арифметика: [инварианты](O-01_INVARIANTS.md). Покрытие: [матрица](O-01_TEST_MATRIX.md). Каждый пример проверяет финансовый результат при принятии предлагаемых имён; публикация примеров не принимает схему за команду.

## 1. Общие предпосылки

Синтетическая группа `100` содержит Тимура `10`, Антона `20`, Дашу `30`. Внешний actor определяется проверенным JWT; реальные JWT и bot-service credentials в документацию не включаются. В расходе автор=плательщик=actor, поэтому предлагаем не принимать `author_id/payer_id`; у компенсации sender=actor, поэтому `sender_id` также не нужен в публичном body. Внутренний bot-service контракт согласовывается отдельно с Тимуром и Лерой.

Предлагаемые поля:

| Поле | Применимость |
|---|---|
| `split_mode` | Обязательный дискриминатор `equal` / `custom` / `by_items` |
| `client_request_id` | UUID для создания расхода/компенсации; scope — группа и тип операции |
| `title` | Название расхода/позиции: на будущей API-границе NFC → Unicode strip → 1..120 code points, запрет Unicode category C (Q-03 утверждён tech lead в Issue #23); точные DTO/операции всё ещё Q-08 |
| `amount` | Общая сумма equal/custom, сумма отдельной позиции или компенсации; всегда строка рублей |
| `participants` | Непустой список уникальных ID для equal или конкретной позиции |
| `shares` | Для custom: список связанных `{user_id, amount}` без отдельного параллельного массива участников |
| `items` | Только by_items; общей `amount` в корне нет |
| `receiver_id` | Только создание компенсации, отличается от доверенного actor |

Поля других режимов отвергаются даже при «правильных» значениях или пустом массиве. Неизвестный/отсутствующий split_mode — 400. Оболочка ошибки уже предусмотрена: `error.code`, `error.message`, `error.request_id`; точные значения code/message здесь не изобретаются. `request_id` диагностики не следует смешивать с UUID идемпотентности.

Числовые суммы в выкладках — копейки; суммы в JSON — строки рублей. Положительный математический знак баланса не является частью утверждённого формата JSON-ответа.

<a id="equal"></a>
## 2. Equal: корректный запрос

`POST /groups/100/expenses`, actor `10`; API-EQ-OK, матрица E-001/E-006.

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000001",
  "title": "Общий расход",
  "split_mode": "equal",
  "amount": "100.00",
  "participants": [30, 10, 20]
}
```

Ожидается расход `10000` коп.; доли `{10:3334,20:3333,30:3333}` несмотря на порядок массива. Если это единственный расход группы, балансы `{10:6666,20:−3333,30:−3333}`. Успешный HTTP-код — Q-07. При отдельном запросе на `"0.01"` доли `{10:1,20:0,30:0}`; у плательщика10 итоговый баланс 0, у остальных 0.

API-EQ-DUP — полный отрицательный пример, матрица E-005; ожидается 400 и отсутствие записи:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000002",
  "title": "Повтор потребителя",
  "split_mode": "equal",
  "amount": "100.00",
  "participants": [10, 10, 20]
}
```

API-EQ-TYPE — число JSON вместо денежной строки, матрица M-007; ожидается 400 без преобразования в строку:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000003",
  "title": "Неверный тип суммы",
  "split_mode": "equal",
  "amount": 100,
  "participants": [10, 20, 30]
}
```

Для проверки плательщика вне потребителей в API-EQ-OK заменить participants на `[20,30]` и использовать новый UUID: доли `{20:5000,30:5000}`, балансы `{10:10000,20:−5000,30:−5000}`. Такой запрос допустим: плательщик остаётся участником группы.

<a id="custom"></a>
## 3. Custom: нулевая доля и точное совпадение

`POST /groups/100/expenses`, actor `10`; API-CU-OK, матрица K-001.

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000004",
  "title": "Явные доли",
  "split_mode": "custom",
  "amount": "100.00",
  "shares": [
    {"user_id": 10, "amount": "0.00"},
    {"user_id": 20, "amount": "40.00"},
    {"user_id": 30, "amount": "60.00"}
  ]
}
```

Доли `{10:0,20:4000,30:6000}`, сумма `10000`. Для изолированного расхода балансы `(10000,−4000,−6000)`. Число записей долей не должно совпадать с числом всех членов группы: разрешено подмножество. Пустое подмножество и отсутствующая сумма записи невалидны.

API-CU-SUM — недостача 1 копейки, матрица K-002; ожидается 400, не исправлять последнюю долю:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000005",
  "title": "Недостача копейки",
  "split_mode": "custom",
  "amount": "100.00",
  "shares": [
    {"user_id": 10, "amount": "40.00"},
    {"user_id": 20, "amount": "59.99"}
  ]
}
```

Замена `"59.99"` на `"60.01"` с новым UUID — отдельный тест превышения 1 копейки, также 400. Отрицательная доля `"-0.01"` отвергается даже если другой долей компенсировано расхождение и общая сумма точна.

<a id="items"></a>
## 4. By items: ресторанный пример

`POST /groups/100/expenses`, actor `10`; API-IT-OK, матрица I-001.

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000006",
  "title": "Ресторан",
  "split_mode": "by_items",
  "items": [
    {"title": "Паста", "amount": "700.00", "participants": [10]},
    {"title": "Стейк", "amount": "1100.00", "participants": [20]},
    {"title": "Салат", "amount": "500.00", "participants": [30]},
    {"title": "Пицца", "amount": "900.00", "participants": [30, 10, 20]}
  ]
}
```

Сервер вычисляет общую сумму `320000` коп. и снимок `{10:100000,20:140000,30:80000}`. При отсутствии других операций балансы `(220000,−140000,−80000)`. Общая `amount` во входе отсутствует. Её наличие в **ответе** допустимо и предусмотрено TD §6.

API-IT-TOTAL — лишняя общая сумма, матрица I-013; ожидается 400 даже при совпадении с суммой позиций:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000007",
  "title": "Нельзя вводить итог отдельно",
  "split_mode": "by_items",
  "amount": "0.02",
  "items": [
    {"title": "Первая", "amount": "0.01", "participants": [10, 20, 30]},
    {"title": "Вторая", "amount": "0.01", "participants": [10, 20, 30]}
  ]
}
```

Удаление общей amount и новый UUID дают отдельный корректный пример API-IT-CENTS (I-002): общая сумма 2 коп., доли `{10:2,20:0,30:0}`. По каждой позиции остаток заново получает минимальный user_id. Делить итог 2 коп. одним equal вместо деления позиций нельзя.

API-IT-EMPTY — пустые потребители позиции, матрица I-005; ожидается 400 и откат всего запроса:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000008",
  "title": "Пустые потребители",
  "split_mode": "by_items",
  "items": [
    {"title": "Позиция", "amount": "1.00", "participants": []}
  ]
}
```

<a id="settlements"></a>
## 5. Частичная компенсация и переплата

Начальное состояние для обоих следующих примеров — ресторан R, без других подтверждённых переводов. Actor `20` (Антон), receiver `10` (Тимур). `POST /groups/100/settlements`.

API-SE-OK, матрица C-001:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000009",
  "receiver_id": 10,
  "amount": "500.00"
}
```

Создаётся pending на `50000` коп., `B=(220000,−140000,−80000)`. Последующий `POST /settlements/{id}/confirm` выполняет только actor10; после commit `B=(170000,−90000,−80000)`. Тело перехода и точный HTTP-код ещё не согласованы; не требуется доверять receiver_id из тела confirm — receiver уже сохранён в записи. Повтор confirm не меняет баланс второй раз.

API-SE-OVER, матрица C-003:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000010",
  "receiver_id": 10,
  "amount": "1400.01"
}
```

Запрос отклоняется с **409** по OS п.5: `140001 > min(140000,220000)=140000`. Pending не создаётся, балансы не меняются. Предел receiver проверяется отдельно в C-004: допустимый долг sender не разрешает превысить положительный баланс выбранного получателя.

API-SE-SPOOF, матрица A-004: actor30 пытается прислать чужого sender. В предлагаемой схеме поле запрещено, ожидается 400; при любом согласованном варианте недопустима запись от имени20.

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000011",
  "sender_id": 20,
  "receiver_id": 10,
  "amount": "500.00"
}
```

<a id="replays"></a>
## 6. Повтор с одинаковым и изменённым содержимым

API-ID-SAME: дважды отправить **точно API-SE-OK** тем же actor20 в группе100, включая UUID `...0009`. Результат — один settlement ID в pending, не два. Балансы как до создания. Это D-003 до confirm; общий контракт повторного создания — TD §5.

После confirm этой записи повторить исходный API-SE-OK. Снова не создавать новую pending; это тот же идентификатор операции. Перевод не прибавляется второй раз, даже если текущий долг уже меньше запрошенной суммы. Семантика тела replay после смены статуса — Q-06; отсутствие дубля — обязательный инвариант.

API-ID-CHANGED — прежний UUID, другая сумма, матрица D-002; ожидается **409**, первоначальная запись остаётся без изменений:

```json
{
  "client_request_id": "00000000-0000-4000-8000-000000000009",
  "receiver_id": 10,
  "amount": "500.01"
}
```

Запрос с тем же UUID от другого actor не считается автоматически разрешённым replay. Авторизация, сравнение тела и политика actor-сопоставления — Q-06. Перестановка consumers не меняет арифметику, но равенство таких запросов по idempotency без согласования не утверждается.

## 7. Дополнительные отрицательные варианты

Для каждого варианта взять соответствующий валидный пример, поменять только указанное поле и использовать новый UUID, чтобы не смешивать ошибку валидации с конфликтом ключа:

| Вариант | Ожидание | Матрица |
|---|---|---|
| Equal `participants=[]` | 400 | E-004 |
| Custom повторяет user_id в двух shares | 400 | K-005 |
| By_items плюс `shares=[]` | 400 после согласования имён | A-008 |
| Equal плюс `items=[]` | 400 после согласования имён | A-008 |
| Custom плюс `participants=[]` | 400 после согласования имён | A-008 |
| `split_mode="weighted"` или поле отсутствует | 400 | A-009 |
| Строка amount=`"0.009"`, `"1e2"`, `"1,00"` | 400, не округлять | M-008/M-009/M-013 |
| Позиция `"0.00"` или `"-1.00"` | 400 | M-005/M-011 |
| Компенсация себе или на `"0.00"` | 400 | C-007/M-012 |
| `client_request_id="not-a-uuid"` | 400 | D-006 |
| Настоящий посторонний пользователь в consumers/receiver | Отказ без записи/раскрытия; exact status Q-07 | E-009/I-016/A-007 |

Кейсы с пробелами, ведущими нулями, отрицательным нулём, нестандартными ID и точными JSON-ответами остаются открытыми. Эти примеры не устанавливают новое правило для них и не заменяют будущую проверку Pydantic-схем/бот-клиента.

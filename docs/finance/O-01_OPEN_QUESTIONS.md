<a id="q-01"></a>
## Q-01. Полная грамматика денежных строк и представление баланса

**Источники:** [PR §3](../PRODUCT_RULES.md), [TD §6](../TECHNICAL_DECISIONS.md), [OS п.1](../roles/OLEG_SPEC.md).

**Не определено:** пробелы по краям, ведущие нули, `+1.00`, Unicode-цифры, `-0.00`, ограничения длины входной строки. Слов «строго две цифры после точки» недостаточно для единственного parser-контракта. Для отрицательных выходных балансов нужно определить знак; явный `+` в математических таблицах не означает обязательный плюс в JSON.

**Примеры:** `" 1.00"`, `"01.00"`, `"+1.00"`, `"١.٠٠"`, `"-0.00"`. Расход с числовым значением ноль уже запрещён независимо от написания; для custom-нулевой доли написание `-0.00` требует отдельного лексического решения.

**Варианты:** (а) канонический ASCII-формат `(0|[1-9][0-9]*)\.[0-9]{2}`, без пробелов/плюса/ведущих нулей; (б) перечисленный набор нормализуемых вариантов с каноническим ответом. Для балансов отдельно согласовать `"-1.00"`, `"0.00"`, `"1.00"` либо другой явный формат. Числа JSON и exponent notation уже запрещены, это не открытый выбор.

**Предложение для обсуждения:** вариант (а), для выходного баланса минус только при отрицательном значении. **Согласуют:** Олег и Тимур; Лера — ввод и отображение. **До:** parser O-02, затем API O-04. Зависимые кейсы M-014–M-016.

<a id="q-02"></a>
## Q-02. Тип user_id и порядок сравнения

**Источники:** PR §3 требует возрастание user_id; TD §6 не фиксирует схемы идентификаторов; [B](../contracts/BOUNDARIES.md) относит users к Тимуру.

**Проблема:** строки `"10"` и `"2"` сортируются иначе, чем целые 10 и 2. Для UUID нужно определить сравнение; bool в Python является подклассом int и не должен незаметно стать ID. Диапазон и представление ID пока отсутствуют.

**Варианты:** положительные целочисленные ID и числовое сравнение; UUID с указанным полным порядком. Входной порядок массива и порядок SQL не заменяют возрастание ID.

**Предложение:** согласовать тип схем users у Тимура, затем закрепить один порядок для split и plan. Примеры O-01 с 10/20/30 — синтетические, а не решение о схеме. **Согласуют:** Тимур и Олег, Лера по JSON. **До:** сигнатуры/валидация O-02 и API O-04. Кейс E-008.

<a id="q-03"></a>
## Q-03. Длина и нормализация названий

**Источник:** PR §1: «названия 1–120 символов»; PR §3: название позиции.

**Проблема:** байты UTF-8, Unicode code points и видимые графемы дают разные длины. Не указаны trimming, название из пробелов, нормализация Unicode и точные поля, к которым применяется предел.

**Пример:** `" "`, `" еда "`, буква с комбинируемым акцентом, emoji из нескольких code points. Простые строки из 120/121 букв `а` не зависят от этих вариантов и уже тестируемы.

**Варианты:** считать code points после явно согласованного trim; считать графемы; не нормализовать и описать точную проверку. **Согласуют:** Олег, Лера, Тимур. **До:** схемы O-04/O-05. Кейсы I-011 и I-012.

<a id="q-04"></a>
## Q-04. Контекстные лимиты сумм и защита агрегатов

**Источники:** PR §1 ограничивает один расход; PR §5 ограничивает компенсацию текущими балансами; TD §2 требует BIGINT; OS п.1 упоминает лимиты parser.

**Проблема:** единый parser с безусловным пределом `100000000` коп. ошибочно запретит возврат долга, накопленного по нескольким расходам. При этом отдельный абсолютный предел компенсации и защита SQL-агрегатов от переполнения не описаны.

**Пример:** два расхода по `100000000` коп., один и тот же плательщик и единственный потребитель. Балансы `(+200000000,−200000000)`. Перевод `150000000` коп. удовлетворяет текущей финансовой формуле, хотя превышает лимит одного расхода. Любой новый дополнительный потолок был бы новым продуктовым ограничением.

**Варианты:** parser только точного формата + явные лимиты по контекстам; общий parser с параметром диапазона; отдельные типы входных сумм. Для агрегатов — явно контролировать диапазон, возвращать проверяемую ошибку/использовать допустимый тип SQL для суммы; не терять точность.

**Согласуют:** Олег и Тимур; Лера по отображению больших долгов. **До:** общая сигнатура parser O-02; хранение и выплаты O-03/O-07. Кейсы M-017, B-008. Значение примера — следствие текущей формулы, не молчаливое введение нового лимита.

<a id="q-05"></a>
## Q-05. Единственный порядок жадного плана

**Источник:** PR §4 даёт сортировку по абсолютному остатку и user_id только как пример; OS п.4 требует стабильный plan.

**Проблема:** не определены возрастание/убывание, статическая сортировка/пересортировка после шага, порядок списка результата. Корректные алгоритмы сохраняют суммы, но дают разные списки переводов.

**Пример:** `B={10:+800,20:+700,30:−700,40:−500,50:−300}`. Статическое убывание даёт `30→10:700`, `40→10:100`, `40→20:400`, `50→20:300`; сопоставление равных 700 первым даёт три перевода.

**Предложение:** один раз сортировать должников и кредиторов по убыванию начального абсолютного остатка, при равенстве — по возрастанию user_id, двигать указатель исчерпанной стороны без пересортировки; возвращать порядок шагов. **Альтернатива:** явно описанный другой greedy. Глобальная минимальность не требуется при любом выборе.

**Согласуют:** Олег и Тимур; Лера по стабильности отображения. **До:** plan O-06 (раньше, если его включат в O-02). Кейс P-005 пока условный; остальные plan-инварианты проверяемы независимо от выбора.

<a id="q-06"></a>
## Q-06. Содержимое идемпотентного запроса и границы доступа к ключу

**Источники:** PR §5; TD §5: уникальность `(group_id, client_request_id)` внутри таблицы, исходный результат или 409 при несовпадении тела; TD §4 и B требуют авторизацию actor.

**Проблемы:** не определены сравнение сырого JSON/нормализованного содержимого, учёт actor, перестановка потребителей/позиций, поведение повторного POST после PUT/soft-delete/confirm и срок хранения результата. Ключ другого участника не должен позволять получить чужой результат или создать объект с чужими полномочиями.

**Примеры:** один ключ, `[10,20]` против `[20,10]`; тот же body от другого actor; повтор создания pending после её confirm и погашения долга; повтор создания уже отредактированного расхода.

**Варианты:** сравнивать нормализованный бизнес-запрос с привязкой к первоначальному actor; сравнивать строго представленное тело и явно документировать чувствительность к порядку. Для последующих изменений выбрать исходный сохранённый ответ либо идентичность записи с текущим представлением, согласовав фразу «первоначальный результат» в TD. Изменение размера scope уникального индекса требует отдельного согласования, оно не вводится здесь.

**Обязательное следствие безопасности:** авторизация и проверка принадлежности результата нужны до replay; повтор с тем же содержимым не создаёт дубль; несовпавшее содержимое — 409. **Согласуют:** Олег, Тимур, Лера (повторы клиента). **До:** O-04/O-07; заранее учесть в моделях O-03. Кейсы D-001–D-006.

<a id="q-07"></a>
## Q-07. Успешные HTTP-ответы, terminal retries и скрытие объектов

**Источники:** PR §5, §7; TD §5–6; OS п.5 прямо указывает «overpayment 409».

**Уже определено:** формат/валидация — 400; нет аутентификации — 401; переплата при confirm — 409, статус остаётся pending; повтор confirm возвращает текущий статус без второго эффекта. Для переплаты создания в матрице использован 409 по OS п.5.

**Открыто:** 200/201/204 на успешные операции и replay; error.code; повтор reject/cancel; несовместимый переход из terminal; 403 или скрывающий 404 для постороннего группы; ответ на ссылку участника/получателя не из группы (валидационный 400 либо скрывающий статус); приоритет ошибок в запросе с несколькими нарушениями. Эти варианты нельзя подставлять произвольно в точные API-тесты.

**Предложение:** 201 при первом создании, 200 при чтении/переходе/replay с телом; одинаковый terminal-переход идемпотентно возвращает текущее terminal, несовместимый — 409; чужая группа — 404, недостаток полномочий внутри доступной группы — 403. Политику нужно согласовать с владельцем auth. В матрице каждая негативная проверка по возможности содержит одно нарушение, чтобы не изобретать приоритет.

**Согласуют:** Тимур, Олег, Лера. **До:** O-04/O-07/O-08. Конкурентные confirm/reject/cancel должны завершаться одним terminal, точный ответ проигравшего зависит от принятой политики. Кейсы C-012, C-013, A-003, X-006.

<a id="q-08"></a>
## Q-08. JSON-поля и операции редактирования

**Источники:** TD §6 задаёт discriminated union и маршруты, но не полные schemas; OS п.3: author=payer; B требует согласования API с ботом.

**Проблема:** названия `amount`, `participants`, `shares`, `items`, `title`, форматы ID, полный PUT, неизменяемые поля и возможность смены payer не утверждены. Подмена actor запрещена независимо от формы JSON.

**Варианты:** связанные custom-записи `{user_id,amount}` либо согласованные параллельные массивы; payer только из actor либо явно передаваемый с проверкой равенства. Не смешивать варианты в одной молчаливой реализации.

В [API-примерах](O-01_API_EXAMPLES.md) предложены связанные записи и отсутствие `author_id/payer_id/sender_id` в публичном body; несвойственные режиму поля запрещены. **Согласуют:** Олег, Тимур, Лера. **До:** O-04/O-05/O-07; формы данных pure functions — до O-02. Ни Pydantic, ни маршруты этим PR не создаются.

<a id="q-09"></a>
## Q-09. Два PUT одного расхода и устаревший пользовательский черновик

**Источники:** TD §5 задаёт атомарный полный PUT под group lock; OS п.3 оставляет version-concurrency «if needed».

**Проблема:** group lock исключает одновременную частичную запись, но не предотвращает перезапись более свежего изменения устаревшим полным телом, поступившим следующим.

**Пример:** оба клиента читают расход 100; первый сохраняет 120, второй сохраняет старый черновик 110. Последовательное применение допустимо по текущему lock-контракту, но UX может требовать отказа второму.

**Варианты:** last-write-wins с явным поведением клиента; версия/ETag с 409 при несовпадении. **Согласуют:** Олег, Тимур, Лера. **До:** O-04. Кейс X-007 до решения проверяет только атомарность и последовательность, не обещает защиту от устаревшего черновика.

<a id="q-10"></a>
## Q-10. Внутренние недопустимые состояния и API-представление нулей

**Источники:** PR §3–4 задаёт нулевые доли и нулевую сумму; PR §7 описывает неожиданные ошибки без раскрытия деталей.

**Проблема:** не определены ответ на повреждённый снимок/несбалансированный вход plan и наличие нулевых записей в API и снимке by_items (включая участника, получившего 0 копеек). Математическое отображение с неявными нулями и список только ненулевых записей эквивалентны для суммы, но не для контрактного теста.

**Примеры:** plan получает `{10:+100,20:−99}`; by_items из двух копеек на троих даёт математически `{10:2,20:0,30:0}`. Нужно ли сериализовать две нулевые строки и всех остальных членов группы в ответе balances?

**Варианты:** сохранять все явно выбранные доли, возвращать все group balances; либо явно оговорить разреженное представление с нулём по отсутствию. Повреждение данных обрабатывать как внутренний отказ с диагностикой без секретов, а не корректировать деньги автоматически.

**Согласуют:** Олег, Тимур, Лера. **До:** снимки O-03/O-05, балансы/plan O-06. Тесты O-01 проверяют отображение с нулём по отсутствию; кардинальность строк и точный вид JSON до решения не фиксируются.

## Что требуется для принятия O-01

Олег проверяет арифметику и полноту матрицы; Тимур — типы, доверенный actor, транзакционный порядок и безопасность replay; Лера — предлагаемые поля, повторы клиента и отображение денежных сумм. Для каждого Q записать принятое решение и его источник в PR/отдельном согласованном изменении, затем обновить зависимые примеры и ожидаемые результаты. Статус O-01 в STATUS не считается завершённым до merge.

Открытые вопросы будущих API-этапов могут остаться явно отложенными, если команда согласует срок решения. Q-01/Q-02 и контракт нужных O-02 функций нельзя выдавать за окончательно согласованные только потому, что этот аудит опубликован.

## Q-01. Полная грамматика денежных строк и представление баланса

**Источники:** [PR §3](../PRODUCT_RULES.md), [TD §6](../TECHNICAL_https://github.com/inte11ectua1/skinulis/issues/11#issuecomment-6425832067S.md), [OS п.1](../roles/OLEG_SPEC.md), [решение Тимура от 26.10.2026](https://github.com/inte11ectua1/skinulis/issues/11#issuecomment-6425832067).

**Утверждено для pure functions и будущей серверной модели.** Вход — строка канонического ASCII-формата `(0|[1-9][0-9]*)\.[0-9]{2}`. Пробелы, ведущие нули, плюс, Unicode-цифры, отрицательные суммы и `"-0.00"` отвергаются обычной валидацией. Числа/bool/null не приводятся к строкам. Trim, нормализации и округления нет.

Formatter принимает целые копейки, включая отрицательные: −101 → `"-1.01"`, −1 → `"-0.01"`, 0 → `"0.00"`, 1 → `"0.01"`; плюс не добавляется. Отрицательное форматирование не разрешает отрицательные расходы. `"0.00"` синтаксически корректна; стоимость расхода/позиции/компенсации проверяется на положительность отдельно, custom-доля допускает ноль. M-014/M-015/M-016 теперь определены на уровне unit.

**История:** в исходном O-01 сравнивались канонический формат и нормализуемые варианты; [предложение Олега](https://github.com/inte11ectua1/skinulis/issues/11#issuecomment-6425190867) и [PR #16](https://github.com/inte11ectua1/skinulis/pull/16) содержали временный предохранитель. Решение Тимура заменяет его обычной ошибкой валидации. Историю исходного аудита сохраняют PR #8 и Git.

**Остаётся до публичного API:** согласовать техническую длину входа и диапазоны агрегатов, не подменяя их лимитом одного расхода. Лера подтверждает UX-ввод/отображение; будущие HTTP-ответы и OpenAPI этим решением не реализованы.

## Q-02. Тип user_id и порядок сравнения

**Источники:** [PR §3](../PRODUCT_RULES.md), [B «Модели»](../contracts/BOUNDARIES.md), [решение Тимура от 26.10.2026](https://github.com/inte11ectua1/skinulis/issues/11#issuecomment-6425832067).

**Утверждено:** внутренний user_id — строго Python int (не bool), диапазон `1..9223372036854775807`. Float, строка, UUID, ноль и отрицательные значения не принимаются. Проверка типов и диапазона выполняется до set/dict и проверки членства, исключая подмену `True == 1` или `1.0 == 1`.

Остаток распределяется по возрастанию числового ID: для [10,2,5] и 100 коп. доли `{2:34,5:33,10:33}` независимо от входного порядка. E-008 теперь имеет точный результат. Временные generic ID и order_key из PR #16 удаляются в follow-up; создание настоящих models users не входит в O-02.

**История:** первоначальный вопрос сравнивал числовые ID, строки и UUID. Платформенный владелец users выбрал положительный signed BIGINT, поэтому этот внутренний выбор больше не TBD. Источники первоначального обсуждения — O-01/PR #8 и [предложение Олега](https://github.com/inte11ectua1/skinulis/issues/11#issuecomment-6425190867).

**Отдельно до OpenAPI:** Лера и Тимур согласуют сериализацию больших ID и обмен с ботом. Подтверждение Леры ещё ожидается; второй внутренний вид идентификатора не вводится.

## Q-03. Длина и нормализация названий

**Источник:** PR §1: «названия 1–120 символов»; PR §3: название позиции.

**Проблема:** байты UTF-8, Unicode code points и видимые графемы дают разные длины. Не указаны trimming, название из пробелов, нормализация Unicode и точные поля, к которым применяется предел.

**Пример:** `" "`, `" еда "`, буква с комбинируемым акцентом, emoji из нескольких code points. Простые строки из 120/121 букв `а` не зависят от этих вариантов и уже тестируемы.

**Решение техлида для будущих DTO расходов и позиций O-04/O-05:** [Issue #23](https://github.com/inte11ectua1/skinulis/issues/23#issuecomment-6467181035). Применить **NFC → Unicode `strip()` → 1..120 Unicode code points → отказ для category C (в том числе ZWJ и управляющих/невидимых символов)**. Внутренние пробелы и регистр сохраняются; из одних пробелов имя не принимается. Это принятое техническое правило **на входе API**, а не новое SQL-ограничение: в Draft O-03 CHECK проверяет только `char_length` 1..120, то есть прямой SQL может записать то, что API отклонит. Нужны тесты граничных Unicode-строк, нормализации и whitespace в O-04/O-05. **Открыто:** самостоятельная оценка Лерой удобства этого ограничения, включая составные emoji; её approval не получен. Исходные вопросы о вариантах выше сохранены как история. Кейсы I-011/I-012.

<a id="q-04"></a>
## Q-04. Контекстные лимиты сумм и защита агрегатов

**Частично подтверждено** [решением Тимура в O-02](https://github.com/inte11ectua1/skinulis/issues/11#issuecomment-6425832067): parser/formatter не получают общий лимит одного расхода; расход — 1–100000000 коп., custom-доля ≥0. **Дополнено для хранения O-03** [решением Тимура в Issue #23](https://github.com/inte11ectua1/skinulis/issues/23#issuecomment-6467181035): строковые денежные значения в БД — точные signed BIGINT; `expense.amount_kopecks` ограничен 1..100000000, shares ≥0, settlement >0 без лимита одного расхода. Положительная хранимая сумма ограничена типом BIGINT, но это **не новый продуктовый потолок долга**. `SUM(bigint)` PostgreSQL возвращает NUMERIC: следующие сервисы используют точные SQL NUMERIC/Python int, без float и рискованного промежуточного сложения BIGINT/cast обратно. **Всё ещё открыты:** публичные ограничения на накопленные суммы/формат их отображения, ошибки при невозможности сохранить крупную отдельную компенсацию и контекстные предохранители O-04/O-07.

**Источники:** PR §1 ограничивает один расход; PR §5 ограничивает компенсацию текущими балансами; TD §2 требует BIGINT; OS п.1 упоминает лимиты parser.

**Проблема:** единый parser с безусловным пределом `100000000` коп. ошибочно запретит возврат долга, накопленного по нескольким расходам. При этом отдельный абсолютный предел компенсации и защита SQL-агрегатов от переполнения не описаны.

**Пример:** два расхода по `100000000` коп., один и тот же плательщик и единственный потребитель. Балансы `(+200000000,−200000000)`. Перевод `150000000` коп. удовлетворяет текущей финансовой формуле, хотя превышает лимит одного расхода. Любой новый дополнительный потолок был бы новым продуктовым ограничением.

**Варианты:** parser только точного формата + явные лимиты по контекстам; общий parser с параметром диапазона; отдельные типы входных сумм. Для агрегатов — явно контролировать диапазон, возвращать проверяемую ошибку/использовать допустимый тип SQL для суммы; не терять точность.

**Согласованное для O-02/O-03:** типы и арифметика выше; **открыто до O-04/O-07** — вопросы публичного ввода и отображения больших сумм, обработка границ. Лера отдельно оценивает UX больших долгов. Кейсы M-017, B-008. Значение примера — следствие текущей формулы, не молчаливое введение нового лимита.

<a id="q-05"></a>
## Q-05. Единственный порядок жадного плана

**Источник:** PR §4 даёт сортировку по абсолютному остатку и user_id только как пример; OS п.4 требует стабильный plan.

**Проблема:** не определены возрастание/убывание, статическая сортировка/пересортировка после шага, порядок списка результата. Корректные алгоритмы сохраняют суммы, но дают разные списки переводов.

**Пример:** `B={10:+800,20:+700,30:−700,40:−500,50:−300}`. Статическое убывание даёт `30→10:700`, `40→10:100`, `40→20:400`, `50→20:300`; сопоставление равных 700 первым даёт три перевода.

**Предложение:** один раз сортировать должников и кредиторов по убыванию начального абсолютного остатка, при равенстве — по возрастанию user_id, двигать указатель исчерпанной стороны без пересортировки; возвращать порядок шагов. **Альтернатива:** явно описанный другой greedy. Глобальная минимальность не требуется при любом выборе.

**Согласуют:** Олег и Тимур; Лера по стабильности отображения. **До:** plan O-06 (раньше, если его включат в O-02). Кейс P-005 пока условный; остальные plan-инварианты проверяемы независимо от выбора.

## Q-06. Первоначальное намерение и replay

**Для Expense O-04 утверждено [Тимуром](https://github.com/inte11ectua1/skinulis/issues/36#issuecomment-6469818682).**
Scope UUID — группа и таблица expenses. Сравниваются actor+group+title после
NFC/strip+mode+integer amount+sorted participants/custom pairs, включая нули.
Перестановки равного набора эквивалентны; equal и custom — разные намерения.
Первый POST сохраняет неизменяемые initial_create_intent/result JSONB и version1
в одной транзакции; result — полная первоначальная mutation envelope.
Replay того же actor/намерения —200 с **исходным** result даже после PUT/DELETE;
другое тело/actor —409 request_conflict без исходных DTO. Сначала membership.
Legacy NULL-history —409 request_history_unavailable владельцу, без восстановления
из текущих долей. Retention — весь срок финансовой строки, включая deleted.
После timeout повторять тот же UUID/исходное намерение, не новый UUID; актуальный
экран читать GET/list. Схема — 0005_expense_replay_version.

Это решение по expenses, не полный контракт будущих settlements O-07; их
state-machine/replay/terminal детали согласуются отдельно. [Полный контракт](../contracts/O-04_EXPENSES.md).

## Q-07. HTTP ответы и безопасные ошибки

**Expense O-04 утверждён [решением Тимура](https://github.com/inte11ectua1/skinulis/issues/36#issuecomment-6469818682).**

POST/PUT/DELETE возвращает {expense,balances}; GET плоский ExpenseProfile.
400 validation_error либо invalid_participants, существующие 401/ambiguous_actor,
404 group_not_found/expense_not_found для чужих/deleted, 403 expense_author_required

с нулями; без confirmed допустим null. POST replay возвращает первоначальные

## Q-08. JSON расходов и полная замена

<a id="q-09"></a>
## Q-09. Optimistic expense version

**Для O-04 принято [решение Тимура](https://github.com/inte11ectua1/skinulis/issues/36#issuecomment-6469818682): optimistic version, без last-write-wins.**
PUT body требует expected_version≥1 (strict JSON int). Под groups FOR UPDATE →
expense FOR UPDATE версия сравнивается; stale —409 expense_version_conflict,
успех — полный снимок и version+1. Первый DELETE active требует положительную
целую query expected_version=N, также сравнивает и увеличивает версию. Повтор
автора уже deleted расхода —200 с прежним tombstone/version даже со старым N;
чужой actor не получает объект. Deleted PUT/GET —404. Ошибка откатывает весь снимок
и версию. После PUT timeout сначала GET и сверка версии/данных, без слепого stale
retry; идемпотентность PUT с отдельным UUID не вводится.

Один group lock обеспечивает атомарность, а version — защиту старого черновика;
эти гарантии не взаимозаменяемы. Миграция и [контракт](../contracts/O-04_EXPENSES.md).

<a id="q-10"></a>
## Q-10. Внутренние недопустимые состояния и API-представление нулей

**Источники:** PR §3–4 задаёт нулевые доли и нулевую сумму; PR §7 описывает неожиданные ошибки без раскрытия деталей.

**Проблема:** не определены ответ на повреждённый снимок/несбалансированный вход plan и наличие нулевых записей в API и снимке by_items (включая участника, получившего 0 копеек). Математическое отображение с неявными нулями и список только ненулевых записей эквивалентны для суммы, но не для контрактного теста.

**Примеры:** plan получает `{10:+100,20:−99}`; by_items из двух копеек на троих даёт математически `{10:2,20:0,30:0}`. Нужно ли сериализовать две нулевые строки и всех остальных членов группы в ответе balances?

**Решение техлида для хранимых снимков O-03/O-05:** [Issue #23](https://github.com/inte11ectua1/skinulis/issues/23#issuecomment-6467181035). Сохранять **все явно выбранные доли**, в том числе `0`, в `expense_shares` и `expense_item_shares`. Отсутствие строки означает **не выбран**, а не «выбран с нулём». Итоговый snapshot `by_items` — union выбранных потребителей позиций, в том числе нулевых. Новый член группы не переписывает прежние снимки. БД хранит неотрицательные значения, но **не подтверждает полноту snapshot или арифметическое равенство сумм**; это задача O-04/O-05 в групповой транзакции.

**Для O-04 принято решением #36:** повреждённый persisted expense snapshot даёт safe500 internal_error без автоисправления; mutation balances при confirmed включает всех членов группы и нули. **Открыто для O-06:** представление отдельного GET /balances/plan и реакция на несбалансированный внутренний вектор. Исторический O-01 не утверждал кардинальность DB/JSON; текущее Expense-решение не закрывает весь Q-10 и не заменяет независимый code review Леры.

Для каждого Q записать принятое решение и его источник в PR/отдельном согласованном изменении, затем обновить зависимые примеры и ожидаемые результаты. Статус O-01 в STATUS не считается завершённым до merge.

Открытые вопросы будущих API-этапов отложены до соответствующих O-04–O-08 с явными границами выше. Q-01/Q-02 приняты отдельным решением Тимура; Q-03 (для финансовых имён), storage-составляющая Q-04 и storage-составляющая Q-10 закреплены решением в Issue #23. Весь Q-04 или Q-10 не считать закрытым; Q-05 остаётся открытым; Q-06–Q-09 для Expense O-04 приняты отдельным решением #36, остальные будущие финансовые операции согласуются отдельно. Принятие документационного PR, независимое ревью и личный клиентский ответ Леры проверяются отдельно.

**Уточнение O-04:** реакция на повреждённый persisted expense snapshot теперь определена как safe500 без автоисправления, mutation balances при confirmed включает всех участников с нулями. Представление отдельного GET /balances/plan и некорректного внутреннего вектора O-06 всё ещё требует отдельного решения; этим Expense-контрактом весь Q-10 не закрывается.

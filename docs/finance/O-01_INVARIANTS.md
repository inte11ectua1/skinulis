<a id="money"></a>
## 1. Денежный домен и ограничения

**INV-M1.** Денежное значение внутри сервиса — целое число копеек. В PostgreSQL денежные столбцы — `BIGINT`. Разбор API-строки и форматирование не проходят через `float`, `round` или binary floating point. Суммирование, сравнение и деление с остатком выполняются над целыми. Источники: PR §1, §3; TD §2, §6; B «Деньги»; OS п.1.

Для уже допустимой строки `R.FF` значение равно `100 × R + FF`; например `"1000000.00" → 100000000`, `"0.01" → 1`. Форматирование неотрицательного целого `A` использует `A div 100` и остаток из двух цифр. Знак **выходного баланса** и лексические варианты входа обсуждаются в Q-01; положительные входные суммы расходов и компенсаций не принимают отрицательных значений.

**INV-M2.** API принимает суммы строками с ровно двумя десятичными цифрами и точкой. JSON-число `100.00`, `true`, `null`, `"1e2"`, `"1,00"`, `"1.0"`, `"1.000"` не удовлетворяют этому контракту. Не выполнять приведение JSON-чисел и автоматическое округление. Полная грамматика с пробелами, знаком плюс, ведущими нулями и Unicode-цифрами ещё не согласована: Q-01.

| Объект | Ограничение | Следствие |
|---|---|---|
| Общая стоимость одного расхода | `1 ≤ A ≤ 100000000` коп. | Границы API: `"0.01"`–`"1000000.00"` включительно |
| Стоимость позиции | Целое `a_j > 0` | Позиция `0` и отрицательная запрещены; её стоимость не может превышать допустимую общую сумму расхода |
| Итоговая/явная custom-доля | Целое `s_u ≥ 0` | Нулевая доля допустима; отрицательная запрещена |
| Компенсация | Целое `x > 0` и ограничение текущими балансами | Лимит одного расхода нельзя автоматически применять к накопленному долгу: Q-04 |
| Состав группы | Не более 30 участников | Любой выбранный набор потребителей — уникальное непустое подмножество этой группы |
| Позиции расхода | Не более 50 | Пустой by_items не может дать положительную стоимость расхода; недопустим |
| Названия | Длина 1–120 по PR §1 | Подсчёт Unicode-символов и обрезка пробелов — Q-03 |

`custom` с пустым списком не может удовлетворить положительной сумме расхода. Набор из 31 участника не может быть подмножеством допустимой группы. Повторяющийся участник отвергается **до** преобразования списка в множество; молчаливое удаление дублей скроет ошибку запроса.

Лимит расхода — общий и для by_items: сначала суммируются целые стоимости всех позиций, затем проверяется предел `100000000`. Две позиции по `60000000` каждая недопустимы: сумма `120000000` превышает лимит. Для 50 позиций нижняя возможная общая сумма — 50 копеек.

Python `int` не переполняется, но отдельные долги, накопленные балансы и суммы SQL не ограничены стоимостью одного расхода. Политика выхода за диапазон хранилища и ограничения агрегатов требуют решения Q-04. Обрезка, насыщение и округление недопустимы.

## 2. Распределение расходов

### Equal: INV-S1

Пусть `A > 0`, уникальный набор потребителей `U`, `n = |U| ≥ 1`. Все потребители и плательщик — участники группы; автор расхода равен плательщику и определяется доверенным actor. Плательщик может отсутствовать в `U` (PR §1–3; OS п.3).

Упорядочить потребителей по возрастанию `user_id`. Для `A = n × q + r`, `0 ≤ r < n`, первые `r` получают `q + 1`, остальные — `q` копеек. Сортировка должна использовать согласованный тип идентификатора, а не случайный порядок JSON или SQL; точный тип — Q-02.

- Сохранение суммы: `Σ s_u = r(q + 1) + (n − r)q = nq + r = A`.
- Неотрицательность: `q ≥ 0`; при `A < n` нулевые доли необходимы.
- Разница любых двух долей не больше 1 копейки.
- Перестановка одного и того же входного набора не меняет отображение `user_id → доля`.
- Остаток распределяется по user_id, а не плательщику, порядку ввода или по жребию.

Для синтетических числовых ID `10 < 20 < 30`: `10000 = 3 × 3333 + 1 → {10:3334,20:3333,30:3333}`; `1 = 3 × 0 + 1 → {10:1,20:0,30:0}`. Один потребитель получает всё. Пустой набор и дубли отвергаются.

### Custom: INV-S2

Явные записи `user_id → s_u` образуют непустой набор без дублей; каждый пользователь из группы; `s_u ≥ 0`; **строго** `Σ s_u = A`. Не компенсировать недостачу, превышение или отрицательное значение автоматически. Пример `A=10000`: `{10:0,20:4000,30:6000}` допустим; суммы `9999` и `10001` недопустимы. Для списка участников и отдельного массива долей, если команда выберет такой JSON, необходимы однозначное соответствие и одинаковые длины; предложенный контракт использует связанные записи (Q-08).

### By items: INV-S3

Позиции `j=1..m`, `1 ≤ m ≤ 50`, имеют положительную стоимость `a_j`, допустимое название и уникальный непустой набор `U_j` из группы. Каждую позицию разделить по equal **независимо**. Общая стоимость `A = Σ_j a_j` вычисляется сервером; отдельное поле общей стоимости запрещено (PR §3; TD §6).

Итоговый снимок: `s_u = Σ_j s_{j,u}`, где отсутствующий в позиции пользователь имеет вклад 0. Тогда `Σ_u s_u = Σ_j Σ_u s_{j,u} = Σ_j a_j = A`. В балансах использовать итоговый снимок `expense_shares` ровно один раз. `expense_item_shares` — детализация, а не второй источник списания.

Один пользователь в разных позициях допустим; дубли внутри одной позиции — ошибка. Наборы потребителей позиций могут различаться. Две позиции по 1 копейке на `{10,20,30}` дают `{10:2,20:0,30:0}`. Деление общей суммы 2 одним equal дало бы `{10:1,20:1,30:0}` и нарушило бы правило независимого деления позиций. «Выравнивать» такие копейки между позициями нельзя без изменения продукта.

Другой пример: `1` на `{10,20}` и `1` на `{20,30}` дают итог `{10:1,20:1,30:0}`. Чаевые и сервисный сбор — обычные положительные позиции; отрицательная скидка не поддерживается. Перестановка позиций сохраняет итоговые доли, но её значение для идемпотентности всего запроса — Q-06.

<a id="balances"></a>
## 3. Балансы и доказательство нулевой суммы

**INV-B1.** Для пользователя `u`:

`B_u = P_u − S_u + T_u − R_u`,

где `P` — оплаченные активные расходы, `S` — итоговые доли только активных расходов, `T/R` — отправленные/полученные только confirmed-компенсации. `B > 0` означает «ему должны», `B < 0` — «он должен». Источники: PR §4–6; TD §5; OS п.4,7.

Каждый активный расход даёт группе `+A` у одного плательщика и суммарно `−A` по снимку. Каждая confirmed-компенсация даёт `+x` отправителю и `−x` получателю. Поэтому `Σ_u B_u = 0`, если все записи принадлежат одной группе, снимки сохраняют сумму, а данные не продублированы соединением таблиц. Участники с нулевым балансом не нарушают доказательство.

**INV-B2.** `pending`, `rejected`, `cancelled` не изменяют `T/R`. Создание pending не резервирует долг: несколько pending на один долг допустимы; их подтверждения повторно ограничены текущими остатками.

**INV-B3.** Снимок старого расхода не пересчитывается после вступления нового члена группы. Новому пользователю начисляется 0 по прошлому расходу. Редактирование заменяет расход и все вложенные доли/позиции атомарно; ошибка возвращает старое состояние целиком. Soft-delete исключает расход и его итоговые доли из `P/S`, сохраняя историю. Confirmed-компенсации никогда не удаляются и не исправляются вслед за изменением расхода.

Контрпример для неверного двойного учёта: у ресторанного примера ниже повторное вычитание детализации позиций даст сумму балансов `−320000`, а не 0. Проверка `Σ B=0` необходима, но недостаточна: одновременное двойное начисление и списание расхода тоже сохранило бы ноль. Поэтому тесты должны проверять **весь вектор балансов**, а не только сумму.

<a id="restaurant"></a>
## 4. Независимая проверка ресторанного сценария

Синтетические участники: Тимур `10`, Антон `20`, Даша `30`. Эти ID служат арифметическому примеру, не фиксируют тип будущих API-идентификаторов.

| Позиция | Всего, коп. | Тимур | Антон | Даша |
|---|---:|---:|---:|---:|
| Паста | 70000 | 70000 | 0 | 0 |
| Стейк | 110000 | 0 | 110000 | 0 |
| Салат | 50000 | 0 | 0 | 50000 |
| Пицца | 90000 | 30000 | 30000 | 30000 |
| Итого | 320000 | 100000 | 140000 | 80000 |

Проверки: `70000+110000+50000+90000=320000`; `90000 div 3=30000`, остаток 0; `100000+140000+80000=320000`.

Тимур оплатил 320000: `B=(320000−100000,0−140000,0−80000)=(220000,−140000,−80000)`, сумма 0. В рублях: `(+2200.00,−1400.00,−800.00)`.

Компенсация Антон → Тимур `50000`: предел `min(140000,220000)=140000`, поэтому частичная сумма допустима. В pending вектор прежний. После confirm `B=(220000−50000,−140000+50000,−80000)=(170000,−90000,−80000)`, сумма 0. Повтор confirm не меняет этот вектор.

Если после confirm удалить ресторанный расход: `P=S=0`, но перевод сохранён; `B=(−50000,+50000,0)`, сумма 0. Тимур теперь должен Антону 50000 копеек — это ожидаемый обратный долг. Если вместо удаления автор заменит расход на 30000 с единственным потребителем Антоном, то `B=(30000−50000,−30000+50000,0)=(−20000,+20000,0)`.

## 5. Жадный план переводов: INV-P1

Источники: PR §4; OS п.4. Набор должников `B<0`, кредиторов `B>0`; нулевые балансы исключены из сопоставления. Сумма всех долгов равна сумме всех требований. На шаге сумма перевода `x=min(остаток долга,остаток требования)>0`; уменьшить оба остатка. Хотя бы одна сторона исчерпана, поэтому алгоритм заканчивается и закрывает все остатки.

Для `d` должников и `c` кредиторов при ненулевом долге жадное сопоставление требует не более `d+c−1` переводов: каждый шаг исчерпывает хотя бы одну сторону, последний — обе. Это верхняя граница для такого алгоритма, **не обещание глобального минимума**. План вычисляется заново, не записывает компенсации и не доказывает внешний банковский перевод.

Требование детерминированности уже есть, но «например сортировка по абсолютному остатку, затем user_id» не определяет направление сортировки и пересортировку после шага. **Q-05 блокирует точные списки переводов для неоднозначных примеров.** Предлагаемая политика для согласования: один раз сортировать обе стороны по убыванию исходного абсолютного остатка, затем по возрастанию user_id; после шага двигаться дальше только у исчерпанной стороны, без пересортировки.

Контрпример к обещанию глобального минимума: `B={10:+800,20:+700,30:−700,40:−500,50:−300}`. Предложенная политика даёт `30→10:700`, `40→10:100`, `40→20:400`, `50→20:300` — четыре перевода. Другая последовательность `30→20:700`, `40→10:500`, `50→10:300` закрывает те же долги за три. Минимизация числа переводов не входит в MVP.

Для однозначного вектора `{10:+100,20:−100}` любой допустимый greedy даёт единственный перевод `20→10:100`. Пустой/полностью нулевой вектор даёт пустой план. Несбалансированный внутренний вектор не должен давать частичный план как успешный результат; способ сообщения о повреждённых данных — Q-10.

## 6. Компенсации и конечный автомат

**INV-C1.** Для sender `s`, receiver `r` и суммы `x` создание и новое подтверждение допустимы только при `s≠r`, членстве обоих в группе, `B_s<0`, `B_r>0`, `0<x≤min(−B_s,B_r)`. Actor для создания — сам sender из проверенной аутентификации. Внешний `sender_id` не является доказательством полномочий. Источники: PR §5; TD §4–6; B «Авторизация»; OS п.5–6.

На confirm в одной транзакции под group lock заново прочитать статус и текущие балансы; проверить права receiver и предел. Проверка при создании не заменяет проверку при confirm. Если долг уменьшился или стороны поменялись ролями — 409, запись остаётся pending, финансового эффекта нет.

**INV-C2.** Успешный confirm меняет балансы на `ΔB_s=+x`, `ΔB_r=−x`, один раз за жизнь записи. Конечные состояния неизменны; повтор того же перехода не создаёт второго эффекта. Повторная попытка несовместимого перехода не может вернуть запись в pending или другой terminal. Точные ответы на повтор reject/cancel и HTTP success-коды — Q-07.

| Исходное состояние | Действие и разрешённый actor | Результат | Изменение балансов / ошибка |
|---|---|---|---|
| Нет записи | Создать: sender | pending | 0; формат/значение 400, нет аутентификации 401; переплата 409 по OS п.5 (уточнить общий error.code в Q-07) |
| pending | confirm: receiver | confirmed | `(+x,−x)` при свежем валидном пределе; иначе 409, остаётся pending |
| pending | reject: receiver | rejected | 0 |
| pending | cancel: sender | cancelled | 0 |
| confirmed | Повтор confirm: receiver | confirmed | 0; TD §5 требует возврата текущего статуса, точный HTTP-код — Q-07 |
| rejected | Повтор reject: receiver | rejected | 0; контролируемый повтор, контракт ответа — Q-07 |
| cancelled | Повтор cancel: sender | cancelled | 0; контролируемый повтор, контракт ответа — Q-07 |
| Любое terminal | Переход в другой статус | Без изменения | Запрещён; предлагается 409, требуется Q-07 |
| Любое | Действие другого члена группы | Без изменения | 403, если объект ему доступен, но нет права перехода |
| Любое | Действие без аутентификации | Без изменения | 401 |
| Любое | Чтение/действие постороннего группы | Без изменения | Без раскрытия объекта; выбор 403/404 — Q-07 |

Права проверяются и на повторе. Владелец группы не получает полномочия подтвердить чужой перевод. Pending не является доказательством долга именно между этими двумя участниками: ограничения основаны на общих нетто-балансах группы.

<a id="transactions"></a>
## 7. Транзакции, конкуренция и идемпотентность

**INV-T1.** Все финансовые изменения одной группы сериализуются: одна DB-транзакция, `SELECT ... FOR UPDATE` строки `groups` **перед** блокировкой операционных записей, затем чтение актуального состояния, проверка и атомарная запись. При ошибке — rollback всей операции. SQLAlchemy sync, Session на запрос; это спецификация будущих тестов PostgreSQL, не реализация БД. Источники: TD §2, §5; B «Транзакции»; OS п.6.

| Конкурентный сценарий | Допустимый результат |
|---|---|
| Два confirm одной pending на 100 | Первый делает confirmed и `Δ=(+100,−100)`; второй видит confirmed. Общий эффект ровно 100, не 200 |
| Две pending по 100 при `B=(+100,−100)` | При отсутствии новых изменений долга подтвердится ровно одна из двух валидных конкурентных попыток; другая 409 и pending, итог `(0,0)` |
| PUT уменьшает расход до confirm | Если PUT зафиксирован первым, confirm проверяет уменьшенный долг и может вернуть 409; если confirm первый, PUT сохраняет уже confirmed перевод и может дать обратный долг |
| Одинаковый client_request_id одновременно | Одна запись и один финансовый эффект; второй запрос воспроизводит результат, а не создаёт дубль |
| Одинаковый ключ, разное содержимое | Один успешный результат, другой 409; первоначальная запись не меняется |
| Любые две финансовые записи группы | Результат эквивалентен одному из последовательных порядков; нет частично заменённых снимков и потерянного подтверждения |

Для сценария PUT/confirm: расход 100 оплатил `10`, потребитель `20`; pending `20→10:100`. PUT меняет сумму на 60. Порядок PUT→confirm: `B=(+60,−60)`, confirm 409, pending. Порядок confirm→PUT: сначала `(0,0)`, затем `B=(−40,+40)`, перевод остаётся confirmed. Оба результата законны; смешанное состояние, например confirmed на основе старых данных после PUT с запрещённой переплатой, — нет.

Ограничение «не больше одной полной компенсации» относится к неизменному исходному долгу. Если новая независимая операция снова создала долг между подтверждениями, второе подтверждение может стать допустимым. Тест должен явно исключать такие изменения, иначе ожидание «никогда две» ошибочно.

**INV-T2.** `client_request_id` — UUID; уникальность `(group_id, client_request_id)` внутри типа операции/таблицы. Одинаковый ключ может существовать в другой группе или в другом типе операции. Совпавший ключ и прежнее содержимое не создают новую запись; несовпавшее содержимое — 409. После авторизации повтор распознаётся до отказа по изменившемуся текущему долгу, иначе успешную операцию невозможно безопасно повторить. Какие поля сравниваются, кто вправе воспроизвести чужой ключ и как представляется первоначальный результат после последующего изменения объекта — Q-06.

Гонку подтверждать отдельными соединениями PostgreSQL с управляемым одновременным стартом/барьерами и проверкой commit/rollback, без предположения о победителе. Это не проверяется mock-сессией и не заменяется `sleep`. Межгрупповая блокировка не требуется моделью group lock; отсутствие случайной глобальной сериализации проверяется отдельно.

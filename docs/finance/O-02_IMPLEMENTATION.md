## Файлы и сигнатуры

Новый пакет `app/services/` содержит только стандартную библиотеку и собственную денежную арифметику. Он не импортирует Settings, FastAPI, Pydantic, SQLAlchemy или Telegram, не читает файлы/сеть/окружение. Входные коллекции не изменяются, результаты создаются заново. Исключения не включают исходные пользовательские значения.

| Функция / тип | Назначение |
|---|---|
| `parse_money(value, *, minimum=0, maximum=None)` | Однозначная строка рублей → целые копейки, затем явно заданные границы |
| `format_money(amount)` | Неотрицательные целые копейки → строка с двумя знаками после точки |
| `validate_amount(amount, *, minimum=0, maximum=None)` | Строгое целое, не bool; проверить контекстный диапазон |
| `validate_expense_amount(amount)` | Проверить ровно один расход: 1–100000000 коп. |
| `split_equal(amount, participants, *, group_members, order_key)` | Остаток первым участникам в явно переданном порядке ID |
| `split_custom(amount, shares, *, group_members, order_key)` | Вход — последовательность пар `(ID, копейки)`; нули допустимы, сумма обязана точно совпасть |
| `ExpenseItem(title, amount, participants)` | Frozen dataclass одной позиции; не схема HTTP/ORM; вложенный входной список не изменяется функциями |
| `split_by_items(items, *, group_members, order_key)` | Вычислить общую сумму и вернуть `(total, shares)`; доли каждой позиции отдельно складываются в один снимок |

Общие ошибки: TypeError для неверного runtime-типа денег/ключа порядка, MoneyError для определённых нарушений суммы/формата, SplitError для неверных коллекций/принадлежности/суммы custom. **ContractPendingError — отдельное ограничение Draft, не пользовательская ошибка будущего API.** Не отображать его автоматически в HTTP 400 и не подключать Draft как окончательный API-валидатор.

## Что остаётся открытым

1. **Q-01.** Уже принятые строки `"100.00"`, `"0.01"`, `"1000000.00"` разбираются точно. Известные ошибки (`"0.009"`, JSON-число, экспонента, запятая, отрицательная ненулевая сумма) отклоняются без округления. Строки с пробелами, плюсом, ведущими нулями, Unicode-цифрами и отрицательным нулём вызывают ContractPendingError: здесь не принято решение об их окончательной допустимости. Форматирование отрицательных копеек также ожидает Q-01. Отрицательные балансы и их сервис не реализуются.
2. **Q-02.** Тип ID не выбран за владельца users. Split-функции параметризованы hashable ID и требуют чистый `order_key(ID) -> int` с уникальным ключом для каждого выбранного ID. Это временный явный контракт математической функции, не новый тип ID API/БД. Для числовых синтетических ID тесты передают identity key; словесные метки в отдельном тесте доказывают независимость от модели. После решения команды утвердить конкретные сигнатуры/валидацию ID; пустые/неподходящие скалярные ID нельзя считать уже проверенными как будущий API-ввод. Bool запрещён, чтобы не подменять числового участника через `True == 1`.
3. **Q-03.** Для обычных названий проверяются границы 1–120 через Python len, без trim/нормализации. Это предлагаемый в комментарии вариант для ревью, не окончательное решение о Unicode-графемах. Название только из пробелов вызывает ContractPendingError. Проверки сложных Unicode-границ I-012 не объявлены реализованным контрактом; они относятся к O-04/O-05.
4. **Q-04.** Generic parser и formatter не используют предел одного расхода как глобальный потолок денег. `parse_money("1500000.01") == 150000001`, но та же сумма недопустима для одного расхода. Это разделение арифметики и контекстной проверки; лимиты будущих долгов/SQL-агрегатов не вводятся. Python int сохраняет точность; ограничения BIGINT относятся к будущему слою хранения.
5. **Q-10.** Математический снимок включает выбранных участников с нулевой долей; не выбранные во всём чеке участники отсутствуют. Это внутренний результат функции, не решение о строках в БД или JSON-ответах.

Ошибки ключа порядка (повторяющийся rank, bool или нецелое значение) отвергаются. Обработчик не использует входной порядок как скрытый способ разрешения ничьей. Чистота и согласованность order_key — обязанность вызывающего кода; stateful/random ключ не является допустимым входным контрактом.

## Арифметика

Для A копеек и n потребителей `q,r = divmod(A,n)`. Первые r получают q+1, остальные q. Сумма `r(q+1)+(n−r)q=A`; каждая доля ≥0, разница ≤1. Для 10000/3 — 3334/3333/3333; для 1/3 — 1/0/0. Payer не требуется среди потребителей; доверенный actor и членство самого плательщика проверит будущий сервис O-04.

В custom нельзя автоматически добавить/вычесть даже копейку: иначе сервер изменит явное указание пользователя и скроет ошибку. Для 10000 допустимо 0+4000+6000, недопустимы 4000+5999, 4000+6001 и −1+10001.

В by_items каждая позиция проходит equal отдельно. Ресторан даёт total=320000, shares={10:100000,20:140000,30:80000}. Две позиции по одной копейке на [10,20,30] дают {10:2,20:0,30:0}; деление общего итога одним equal дало бы другое распределение. В результате возвращается только общий итог и единый снимок: повторного списания детализации нет.

Группа проверяется как переданный контекст: 1–30 уникальных членов; каждый потребитель из неё. Список позиций — 1–50; стоимость каждой положительна; сумма всего расхода ≤100000000. Некорректный поздний элемент не меняет входные данные и не оставляет частичных внешних записей: I/O вообще нет.

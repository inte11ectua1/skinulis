## Файлы и сигнатуры

Новый пакет `app/services/` содержит только стандартную библиотеку и собственную денежную арифметику. Он не импортирует Settings, FastAPI, Pydantic, SQLAlchemy или Telegram, не читает файлы/сеть/окружение. Входные коллекции не изменяются, результаты создаются заново. Исключения не включают исходные пользовательские значения.

| Функция / тип | Назначение |
|---|---|
| `parse_money(value, *, minimum=0, maximum=None)` | Каноническая ASCII-строка рублей → целые копейки, затем явно заданные границы |
| `format_money(amount)` | Целые копейки → строка с двумя знаками; отрицательные с минусом, положительные без плюса |
| `validate_amount(amount, *, minimum=0, maximum=None)` | Строгое целое, не bool; проверить контекстный диапазон |
| `validate_expense_amount(amount)` | Проверить ровно один расход: 1–100000000 коп. |
| `split_equal(amount, participants, *, group_members)` | Остаток первым участникам по возрастанию числового ID |
| `split_custom(amount, shares, *, group_members)` | Вход — последовательность пар `(ID, копейки)`; нули допустимы, сумма обязана точно совпасть |
| `ExpenseItem(title, amount, participants)` | Frozen dataclass одной позиции; не схема HTTP/ORM; вложенный входной список не изменяется функциями |
| `split_by_items(items, *, group_members)` | Вычислить общую сумму и вернуть `(total, shares)`; доли каждой позиции отдельно складываются в один снимок |

Ошибки: TypeError для неверного runtime-типа строки, копеек или ID; MoneyError (ValueError) для неканонической денежной строки/недопустимой суммы; SplitError (ValueError) для диапазона ID, неверных коллекций, членства или суммы custom. Исключения не включают исходные значения. **ContractPendingError сохранён только в splits.py для открытого Q-03 о названиях**; parser/formatter больше его не используют. Отображение ошибок в HTTP относится к будущему API.

## Утверждённые контракты

1. **Q-01:** parser принимает только `(0|[1-9][0-9]*)\.[0-9]{2}` в ASCII. `"01.00"`, `"+1.00"`, пробелы, Unicode-цифры, `"-0.00"`, отрицательные суммы, экспонента и лишние разряды вызывают MoneyError. Числа/bool/null не приводятся к строке. Trim, нормализации и округления нет. `"0.00"` синтаксически корректна, но не подходит положительной стоимости расхода/позиции. Formatter: −101 → `"-1.01"`, −1 → `"-0.01"`, 0 → `"0.00"`, 1 → `"0.01"`. Signed output не разрешает отрицательные входные расходы.
2. **Q-02:** внутренние ID — строго Python int в `1..9223372036854775807`, не bool. Float/str/UUID и прочие типы отвергаются, в том числе до set/dict: нельзя подменить ID через `True == 1` или `1.0 == 1`. Все три функции используют этот контракт и встроенную числовую сортировку. Для [10,2,5] и 100 коп. результат `{2:34,5:33,10:33}`. Generic UserId и order_key удалены; ExpenseItem больше не generic. Реальных models users в O-02 нет.
3. **Q-04:** parser/formatter не получают глобальный потолок одного расхода: `parse_money("1500000.01") == 150000001`, но расход на эту сумму недопустим. Expense — 1–100000000 коп., custom-доля ≥0. Контекстная проверка отдельная, новых бизнес-лимитов нет.

## Оставшиеся вопросы

- **До публичного API:** согласовать технический предел длины входа и диапазоны значений. Python int точен, но разбор очень длинной строки потребляет ресурсы; отсутствие лимита в pure parser не является разрешением бесконтрольного публичного ввода. SQL-агрегаты/переполнение отдельно проверить до O-03/O-07. Нельзя заменять эти решения лимитом одного расхода.
- **Лера / OpenAPI:** подтвердить клиентский ввод/отображение денег и обмен ID; особенно сериализацию больших целых у клиентов. Внутренний числовой тип уже утверждён, второй тип ID не вводится. В будущем UX может явно преобразовывать пользовательский ввод до API по отдельному согласованию.
- **Q-03:** обычная длина названия пока проверяется Python len, без trim/нормализации; это прежний вариант PR #16 для ревью, не окончательное решение о Unicode-графемах. Название только из пробелов всё ещё вызывает ContractPendingError. I-012 относится к будущим O-04/O-05.
- **Q-05–Q-10:** этим решением не утверждены. Нулевые доли сохраняются в математическом снимке как раньше; это не решение о строках БД или JSON.

## Арифметика

Для A копеек и n потребителей `q,r = divmod(A,n)`. Первые r получают q+1, остальные q. Сумма `r(q+1)+(n−r)q=A`; каждая доля ≥0, разница ≤1. Для 10000/3 — 3334/3333/3333; для 1/3 — 1/0/0. Payer не требуется среди потребителей; доверенный actor и членство самого плательщика проверит будущий сервис O-04.

В custom нельзя автоматически добавить/вычесть даже копейку: иначе сервер изменит явное указание пользователя и скроет ошибку. Для 10000 допустимо 0+4000+6000, недопустимы 4000+5999, 4000+6001 и −1+10001.

В by_items каждая позиция проходит equal отдельно. Ресторан даёт total=320000, shares={10:100000,20:140000,30:80000}. Две позиции по одной копейке на [10,20,30] дают {10:2,20:0,30:0}; деление общего итога одним equal дало бы другое распределение. В результате возвращается только общий итог и единый снимок: повторного списания детализации нет.

Группа проверяется как переданный контекст: 1–30 уникальных членов; каждый потребитель из неё. Список позиций — 1–50; стоимость каждой положительна; сумма всего расхода ≤100000000. Некорректный поздний элемент не меняет входные данные и не оставляет частичных внешних записей: I/O вообще нет.

# T-05 — users и публичная аутентификация

**Статус: предложено для независимого review, не принятый заранее контракт.**
Issue [#21](https://github.com/inte11ectua1/skinulis/issues/21),
[контрактный checkpoint с Олегом и Лерой](https://github.com/inte11ectua1/skinulis/issues/21#issuecomment-6436016259).
База реализации — main после PR #25. Группы/Telegram actor/bootstrap/link
относятся к T-06; финансовые модели — O-03, бот — L-03.

## Модель и FK

Единая `app.models.User`, metadata `app.models.Base`, таблица `users`:

| Поле | PostgreSQL | Правило |
|---|---|---|
| id | BIGINT GENERATED BY DEFAULT AS IDENTITY | NOT NULL, PK pk_users, >0, максимум signed BIGINT 2^63−1 |
| email | VARCHAR(254) | nullable, canonical ASCII email, uq_users_email |
| password_hash | VARCHAR(255) | nullable, только Argon2id encoding; не публичное поле |
| telegram_id | BIGINT | nullable, >0, uq_users_telegram_id |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |

Ограничения CHECK: `ck_users_id_positive`, `ck_users_telegram_id_positive`,
`ck_users_identity_present` (email или Telegram ID), `ck_users_email_password_pair`
(email/password_hash одновременно NULL либо оба заполнены),
`ck_users_email_normalized` (3–254, lowercase, trim, ASCII без whitespace),
`ck_users_password_argon2id` (Argon2id prefix).

API-only: email + hash, Telegram ID NULL. Telegram-only: Telegram ID,
email/hash NULL. Связанный аккаунт может иметь оба идентификатора, но операция
привязки здесь не реализована. PostgreSQL UNIQUE допускает несколько NULL.
PK и две UNIQUE constraints создают свои индексы; дублирующих индексов нет.
DB проверяет структурные инварианты, а полную email-синтаксику и криптографическую
корректность хэша обеспечивает API/argon2-cffi, не SQL prefix CHECK.

**Олегу / T-06:** ссылаться на `users.id` через signed BIGINT FK. Не создавать
вторую users и не каскадировать удаление финансовой истории; интеграционный
FK-probe проверяет совместимость с ON DELETE RESTRICT. Имена/правила окончательных
FK согласуются в соответствующей задаче. Groups и их FK в T-05 отсутствуют.

Ревизия `0002_users` → `0001_baseline`; одна цепочка/head. Upgrade создаёт users,
повторный upgrade пустой; `alembic check` сверяет ORM. Downgrade удаляет users,
поэтому не является безопасным откатом данных и не выполняется на пользовательской
БД. Следующие миграции создавать от принятого head main после merge T-05.

## Email и пароль

Email ограничен 254 символами на входе; внешние пробелы убираются. Библиотека
email-validator проверяет синтаксис без DNS-запросов, SMTPUTF8 local part запрещён,
IDNA-домен приводится к ASCII. Затем **весь адрес lowercase**, включая local part:
это явная case-insensitive политика identity сервиса. Dots и +tag не удаляются,
разные адреса провайдеров не объединяются. Unicode local part не поддерживается.
DB CHECK не даёт прямой вставке обойти canonical representation и UNIQUE.

Регистрация: 15–128 Unicode символов, не whitespace-only, без control/surrogate/
прочих Unicode category C. Пароль не обрезается и не нормализуется; пробелы внутри
и по краям значимы. Login принимает 1–128 символов с той же проверкой допустимых
символов: неверный короткий пароль даёт 401, пустой/невалидный ввод — 400.
Обязательных правил «цифра/заглавная/символ» нет, допустимы длинные passphrases.

argon2-cffi 25.1.0, профиль RFC_9106_LOW_MEMORY: **Argon2id v19, memory 65536 KiB,
time=3, parallelism=4, salt=16 bytes, hash=32 bytes**. Соль генерирует библиотека
на каждый hash; одинаковые пароли дают разные encoded hashes. Параметры/соль
содержатся в encoding. Plaintext не сохраняется. Регистрация хэширует до открытия
DB-транзакции; INSERT/flush/commit атомарны. Нарушение именно uq_users_email даёт
409 и rollback, другие ошибки не маскируются под конфликт email.

Login сравнивает через Argon2; неизвестный email или отсутствие password credential
также выполняют dummy verification. Все эти случаи, включая неверный пароль,
возвращают одинаковые code/message 401. Это уменьшает разницу вычислительной
работы, но не обещает абсолютно одинаковое время сетевого ответа. Автоматическая
ротация параметров/rehash при login пока не добавлена.

## JWT и dependency

Выбрана PyJWT 2.15.1: поддерживает подпись, allowlist алгоритмов, обязательные
claims, issuer/audience/time validation; для HS256 не требует cryptography extra.
Не используем собственную криптографию. Алгоритм **только HS256** зафиксирован
серверным кодом, не берётся из заголовка JWT/клиентского JSON или произвольной env.
Для одного API signing key это минимальный вариант; алгоритм/TTL вынесены на review.

- `JWT_SECRET_KEY`: случайный, минимум 32 UTF-8 bytes, без default. Для API
  отсутствие/короткий ключ блокирует создание приложения с безопасной ошибкой.
  Settings repr скрывает ключ. Миграционная команда не вызывает проверку JWT,
  migrate-контейнер не получает JWT env и успешно работает без ключа.
- `JWT_ACCESS_TOKEN_TTL_MINUTES`: default **15**, допустимо 1–60. `expires_in`
  в ответе — секунды. Смена ключа инвалидирует ранее выданные tokens.
- Обязательны `sub` (canonical decimal string положительного signed BIGINT),
  целочисленные `iat`, `nbf`, `exp`, `iss=skinulis`, `aud=skinulis-api`,
  `token_use=access`. TTL токена >0 и <=3600 секунд, без clock-skew leeway.
- Подпись/time/issuer/audience проверяются до чтения sub. `alg=none` и другие
  алгоритмы отвергаются. Token больше 4096 символов не разбирается.
- `app.api.dependencies.get_current_user` принимает только HTTP Bearer,
  возвращает ORM User после проверенного JWT и SELECT из текущей request Session.
  Удалённый/несуществующий пользователь → 401, даже если подпись верна.

Refresh, logout/revocation storage, OAuth, email confirmation, password reset,
rate limiting и production HTTPS здесь не реализованы. JWT короткоживущий, но
не шифрует payload; не добавлять в claims пароли, email или секреты. Публичный
email/password login нельзя переносить в Telegram. Bot-service actor в T-06
должен иметь отдельную схему доверия/credential, не произвольный Telegram ID в JSON.

## HTTP DTO и ошибки

Живой OpenAPI — `/openapi.json`, Swagger — `/docs`. Input forbids extra fields:
`user_id`, `telegram_id`, `author_id` не являются доказательством полномочий.
Ниже **только placeholders**, не готовые credentials.

| Метод | Input | Success |
|---|---|---|
| POST /auth/register | JSON email/password | 201 UserProfile, без автоматического login |
| POST /auth/login | JSON email/password | 200 TokenResponse; Cache-Control no-store |
| GET /users/me | Authorization: Bearer <access-token> | 200 UserProfile только текущего actor |

```json
{"email":"alice@example.com","password":"<15-128-character-passphrase>"}
```

```json
{"id":1,"email":"alice@example.com","telegram_id":null,"created_at":"2026-10-27T00:00:00Z"}
```

```json
{"access_token":"<access-token>","token_type":"bearer","expires_in":900}
```

UserProfile допускает nullable email/telegram_id и не содержит hash. IDs — JSON
integers, не UUID. `/users/me?user_id=2` по-прежнему возвращает actor из JWT;
query не меняет права/профиль. Endpoint изменения другого пользователя отсутствует.

| HTTP | error.code | Значение |
|---|---|---|
| 400 | validation_error | Невалидный body/JSON/поля, без исходного ввода |
| 401 | invalid_credentials | Неверная пара login/password |
| 401 | invalid_token | Нет/невалидный/истёкший JWT либо пользователя уже нет |
| 409 | email_already_registered | Canonical email уже занят |
| 500 | internal_error | Неожиданный сбой, без внутренней диагностики |

Все ошибки имеют `error.code/message/request_id`, X-Request-ID, для 401 также
WWW-Authenticate Bearer. Валидация — HTTP 400 вместо 422; OpenAPI содержит 400 и
общую 4XX-схему. Серверная middleware ловит неожиданный сбой до его повторного
выбрасывания в Uvicorn; логирует только сгенерированный request_id без exception
args/body/Authorization. Старые system endpoints и health 503 сохраняются.

## Проверка и следующие задачи

Локально: Ruff, mypy, pytest unit и существующий PostgreSQL runner из README.
Root test fixture генерирует свежий JWT key в памяти на каждый тест, не использует
ключ оператора. Mypy `explicit_package_bases=true` различает два namespace
conftest-модуля; strict режим и состав проверяемых файлов не ослаблены.

Integration использует реальные UUID-БД: clean/repeat migrations, metadata check,
CHECK/UNIQUE/FK, rollback, Telegram-only, две регистрации, concurrent duplicate,
register→login→me, подделка/expiry/alg-none/missing claim и удалённый actor.
Docker smoke выполнялся в отдельном project/volume: db healthy, migrate exit 0,
api healthy, health/docs 200, register 201/login 200/me 200/no token 401,
current=head=0002_users, alembic check без drift, повтор migrate без JWT успешен.
Секреты генерировались локально, логи проверены на их отсутствие. Контейнеры
остановлены через down без -v; пользовательские БД и volumes не удалялись.

**До зависимых изменений:** Олег проверяет users.id/FK и порядок ревизий; Лера —
UserProfile и error DTO. T-06 согласует bootstrap/link/Telegram actor, groups,
invites и UQ-01/02/04/05 отдельно. Текущие DTO не объявлены принятыми до review.

Источники решений: [PyJWT API](https://pyjwt.readthedocs.io/en/stable/api.html),
[профили Argon2](https://argon2-cffi.readthedocs.io/en/stable/parameters.html),
[OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

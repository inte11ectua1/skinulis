# L-05 — согласование API для уведомления о pending

**Статус: требуется решение Тимура и Олега; это не утверждённый API-контракт.**
Задача [#48](https://github.com/inte11ectua1/skinulis/issues/48),
PR [#54](https://github.com/inte11ectua1/skinulis/pull/54).

## Решение и фактический блокер

[Тимур решил реализовать уведомления в текущей L-05](https://github.com/inte11ectua1/skinulis/pull/54#issuecomment-6543837089).
Исключения из PRODUCT_RULES §7 нет. Отдельного согласования маршрута и DTO
уведомлений пока нет. Добавленный checklist до merge ещё не выполнен.

Проверена актуальная main `b055b7e` и merged T-08/O-07:

- MemberProfile содержит user_id, joined_at, is_owner, но не Telegram-привязку.
- SettlementMutation содержит только settlement; Telegram-адресата нет.
- GET /internal/users/me возвращает профиль текущего проверенного actor,
  а не произвольного получателя. Нельзя подменять actor для поиска другого человека.
- Статусы POST 201/200 различают создание и replay, но потерянный ответ 201
  восстанавливается как 200. Исторический pending не доказывает текущий статус
  и не даёт права повторно уведомлять о новой заявке.
- Разрешённого сервисного механизма получения адресата/одноразового разрешения
  на уведомление в фактических маршрутах и схемах нет.

Поэтому нельзя закончить доставку одним изменением Telegram-handler без нового
согласованного backend-контракта. Бот не получает доступ к БД, не использует user_id
как chat_id и не подменяет X-Telegram-ID заголовком получателя.

## Конкретный запрос владельцам backend

Тимур (identity/auth) и Олег (settlements), согласуйте минимальную внутреннюю
операцию, которая позволяет боту **один раз получить разрешение на попытку
уведомить получателя конкретной pending-заявки**, включая восстановление после
потерянного ответа финансового POST. Точные метод, маршрут, DTO, ошибки и способ
хранения решения должны быть утверждены вами до реализации. Здесь новые URL
и поля не вводятся.

Предлагаемые требования для рассмотрения, а не принятое архитектурное решение:

1. Только защищённый bot-service канал с проверенным текущим sender из Update;
   без публичного JWT mirror и без клиентского выбора Telegram-адресата.
2. Сервер сам проверяет доступ, sender, текущий pending и серверную привязку
   receiver. Telegram identity не появляется в публичных ответах/списках участников.
3. Для нового pending с привязкой сервер разрешает одну попытку в соответствующий
   приватный чат. При отсутствии привязки возвращает безопасный результат без доставки.
4. Повторные callbacks, UUID replay, поиск статуса и рестарт не выдают новое
   разрешение. Исторический replay после terminal не разрешает уведомление.
5. Разрешение сериализуется с terminal-переходами; решение о pending принимает
   сервер, а не старый снимок бота. Изменение статуса после выдачи разрешения
   всё равно возможно: текст уведомления не должен обещать неизменность статуса.
6. Сбой/timeout получения разрешения или Telegram SendMessage не вызывает
   финансовый POST, не отменяет pending, не меняет баланс. Неопределённая доставка
   не повторяется автоматически. Пропуск уведомления допустим для best effort;
   повторный спам и гарантированная доставка не обещаются.
7. Уточнить, требуется ли постоянная отметка попытки на сервере и соответствующая
   миграция. MemoryStorage/dedup бота не обеспечат это после рестарта. Backend
   и миграции реализует их владелец отдельным согласованным изменением.
8. Не логировать chat identity, сумму, токен, URL или Telegram exception payload.
   Для диагностики достаточно безопасной категории исхода без персональных данных.

Вопросы к решению: где и как фиксируется однократность, как обрабатывается timeout
самого разрешения, какие HTTP/DTO означают отсутствие привязки/terminal/повтор,
какая проверка T-06 обязательна. Получение адресата без согласованной семантики
однократности не закрывает зависимость.

## Telegram-часть после утверждения контракта

Текст: «Для вас есть заявка на подтверждение перевода. Откройте /start →
Ожидают подтверждения, чтобы проверить актуальные сведения. Подтверждайте только
реально полученные деньги. Бот не выполняет банковский перевод».

Минимальный текст не раскрывает финансовые подробности на экране уведомлений,
не обещает текущий pending после возможной гонки и не переносит кнопки/nonce
из FSM отправителя в приватный чат получателя. В меню получатель проходит
собственную авторизацию и получает актуальный список.

После согласования: typed HTTP-клиент → серверное разрешение → одна ограниченная
по времени попытка SendMessage в проверенный приватный чат. Ошибка доставки
обрабатывается отдельно от результата финансового POST. Incoming pending работает
независимо от уведомлений.

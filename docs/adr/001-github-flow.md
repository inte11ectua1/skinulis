# ADR 001 — GitHub Flow и защита основной ветки

- **Статус:** принято (PR #6 одобрен Лерой и объединён с `main` 16.10.2026; [доказательство](https://github.com/inte11ectua1/skinulis/pull/6)).
- **Дата:** 16 октября 2026 года
- **Ответственный:** Тимур (technical lead)
- **Участники решения:** Тимур, Олег, Лера
- **Связанная задача:** [T-01, issue #2](https://github.com/inte11ectua1/skinulis/issues/2)

## Контекст и проблема

«Скинулись» разрабатывают три человека в одном GitHub-репозитории. У каждого свой участок ответственности: Тимур — платформа, безопасность и DevOps; Олег — финансовая логика и база данных; Лера — Telegram-бот и пользовательские сценарии.

Нужен простой, проверяемый порядок внесения изменений, чтобы:
- основная ветка оставалась пригодной к интеграции и демонстрации;
- изменение чужой области ответственности не попадало в код без ревью;
- история PR, коммитов и проверок показывала индивидуальный вклад;
- после появления CI неудачные проверки блокировали объединение.

Выбор процесса разработки — решение команды, а не утверждение о том, что все настройки GitHub уже включены.

## Решение

**Используем GitHub Flow** в одном репозитории.

1. **`main` — стабильная интеграционная ветка.** Работу над задачами в ней напрямую не ведём.
2. **Одна задача — отдельная короткоживущая ветка.** Именование: `feat/T-02-name`, `feat/O-02-name`, `feat/L-02-name`, `fix/...`, `docs/...` или `chore/...`. Имя связываем с issue, когда это применимо.
3. **Изменения в `main` — только через Pull Request.** В описании указываем связанную задачу, что изменено, как проверено, риски и изменения контрактов. Коммиты оформляем по Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `chore:`).
4. **Командный стандарт — минимум один независимый approval перед merge.** Автор не заменяет независимое ревью самооценкой. **Фактическая защита GitHub теперь допускает исключение для администратора** (по состоянию на 27.10.2026 checks enforcement=non_admins, PR #19 объединён без зарегистрированного approval), поэтому этот стандарт не гарантируется настройками для владельца. Такое исключение использовать осознанно и фиксировать в PR; изменения доменов по возможности согласовывать с владельцами.
5. **Настраиваем branch protection / ruleset для `main`:**
   - требование PR и как минимум одного approval;
   - сброс устаревших approvals после новых коммитов;
   - требование разрешить review conversations;
   - запрет прямого push, force-push и удаления `main`;
   - для обычных участников нет обхода; административный bypass — осознанное изменение владельца после исходного ADR, отмечать его отдельно.
6. **После появления CI** добавляем обязательные status checks. Планируемые проверки на PR: Ruff lint/format, mypy, pytest с PostgreSQL и покрытием не ниже 60%, сборка Docker. Красная или незавершённая обязательная проверка должна блокировать merge.
7. **После merge** удаляем задачу-ветку; в настройках репозитория включаем автоматическое удаление объединённых веток.
8. **Развёртывание не запускаем из непроверенных PR.** Публикация образа и production-deploy разрешаются только после успешного merge в защищённую `main` (либо через отдельно разрешённый ручной запуск); production-секреты не передаются workflow на PR.

Точные команды проверок и правила внесения изменений описаны в [CONTRIBUTING.md](../../CONTRIBUTING.md), [TEAM_WORKFLOW.md](../TEAM_WORKFLOW.md) и [TECHNICAL_DECISIONS.md](../TECHNICAL_DECISIONS.md).

## Рассмотренные альтернативы

| Подход | Почему не выбрали |
|---|---|
| Прямые коммиты в `main` | Проще на старте, но отсутствует обязательное независимое ревью; выше риск сломать общую ветку и сложнее подтвердить процесс проверки. |
| Git Flow с постоянными `develop` и release/hotfix-ветками | Даёт явные релизные потоки, но для команды из трёх человек и одного MVP создаёт лишние ветки, merge и накладные расходы. |
| GitHub Flow | Минимум постоянных веток, короткие PR, понятные проверки и история решений. Выбран. |

## Следствия и компромиссы

**Плюсы:** проверяемая история участия, более раннее обнаружение проблем, понятная интеграция частей API/бота/финансового сервиса и единый путь к CI/CD.

**Минусы:** ожидание ревью может задерживать интеграцию; конфликты веток придётся разрешать до merge; дисциплина небольших PR и актуальных тестов обязательна.

Для срочных исправлений предпочитаем короткий PR с ускоренным ревью. Административный обход технически возможен, но он снижает доказательность обязательного human review/CI; фиксируйте случаи обхода в истории PR. Возвращение одинаковой защиты для всех или дальнейшие изменения политики — через отдельное согласование и PR.

## Подтверждение T-04 (Issue #13 закрыта после merge PR #19; G1 отдельно)

Workflow и стабильные check run names `lint`, `types`, `tests`, `docker-build`,
`ci` выполнены на GitHub. Параметры защиты, красный run, API BLOCKED
и оставшаяся визуальная проверка: [CI evidence и инструкция администратора](../operations/CI.md).
Общий `BLOCKED` при одновременно отсутствующем approval не выдаётся за
визуальное доказательство причины; незакрытые пункты выше сохранены.

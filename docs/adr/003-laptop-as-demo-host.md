# ADR 003 — Ноутбук вместо VPS для учебного хостинга

**Статус:** предложено для командного ревью в PR (2026-11-01). **Решение руководителя проекта:** постоянный VPS и отдельный публичный домен на этапе M5 не закупаются; временный host — личный ноутбук Тимура.

## Контекст и расхождение с исходным планом

До этого в `docs/TECHNICAL_DECISIONS.md`, T-09 #59 и G5 зафиксированы VPS + SSH CD + публичный Caddy HTTPS + проверка `/internal`. Код этой инфраструктуры уже вошёл в `main` через PR #64. Перенос **не удаляет прошлые реализации/тесты** и не означает, что исходные требования преподавателя автоматически изменились.

**Проверка требований курса:** нужен отдельный письменный checkpoint/согласование: локальный laptop-host + исходящий Telegram long polling **не** доказывают публичный HTTPS, SSH deployment на VPS, круглосуточную доступность или изоляцию public `/internal` через работающий Caddy. До подтверждения эквивалентности преподавателем старый G5 следует отмечать «не verified (scope changed)», даже если внутренний локальный M5 принят.

## Решение

- Один ноутбук хостит `db` (PostgreSQL 17, именованный volume), `migrate` (одноразовый Alembic), `api` (FastAPI) и **один** `bot` (aiogram long polling) под Docker Compose. `api` доступен с хоста **только по 127.0.0.1**, не из LAN/Интернета; у DB нет опубликованных портов.
- `bot` соединяется с `api` через внутреннюю Docker сеть, наружу обращается только **исходящими соединениями к Telegram**. Ни публичный IP, ни проброс портов, ни Caddy, ни сертификат, ни домен для этого режима не нужны.
- `compose.yaml` остаётся стандартной локальной базой API/DB; `compose.laptop.yaml` явно добавляет **profile `polling`**. Настоящий бот **не стартует автоматически от обычного `docker compose up`**; запуск только через отдельную явную команду оператора с корректным Telegram-токеном. Не использовать тот же токен одновременно на ноутбуке и другом polling-инстансе.
- GitHub Actions сохраняет CI, безопасный доверенный main release и GHCR images. **Не включать** прежний `workflow_dispatch operation=deploy`, production rollout flag или SSH job: они относятся к архивной VPS инфраструктуре и не используются для laptop-handoff. Не добавлять постоянный self-hosted runner на ноутбук и не открывать сервер по SSH из Интернета.
- Для обновления на ноутбуке выбрать простой **ручной pull/frozen sync/rebuild Compose** от проверенного `main` либо — отдельно проверенный GHCR digest. В текущем локальном сценарии сборка из свежей `main` допустима и проверяется `/version` через `APP_COMMIT_SHA`; **не выдавать это за автоматический CD на сервер**.
- `production` env на VPS, публичные порты 80/443 и Caddy в laptop-режиме не используются. Секреты только в локальном неотслеживаемом `.env`; не копировать в Issue, Actions, журнал/скриншоты.
- Данные группы и расходы остаются в именованном Docker volume **между перезапусками**, но их потеря возможна при удалении volume, поломке диска, утрате ноутбука. Нужны ручные безопасные backup/restore и не публиковать реальные персональные данные.
- Ноутбук может спать/терять Wi-Fi/выключаться; в это время Telegram updates не обрабатываются. Возможность получения старых updates после возобновления зависит от правил Telegram Bot API, не гарантирована для всех событий. Telegram-сообщения **не делают настоящие банковские переводы**.

## Laptop gate M5-L (вместо неизменного оригинального G5)

1. Из чистого clone `main` и отдельной тестовой `.env` воспроизводимо поднимаются `db→migrate→api`.
2. `/health` на `127.0.0.1` проверяет БД, `/version.commit_sha` соответствует проверенному SHA или явно зафиксированному local build SHA; API/DB недоступны через публичные порты. Внешний `/internal` недоступен потому, что HTTP вообще не выставлен наружу; внутренний actor обслуживает только бота.
3. Без Telegram polling по умолчанию; только после разрешённого пользователем локального запуска один bot container общается с API. Реальное Telegram QA — отдельный запуск/подтверждение и отдельные gates G2–G4; mocked integration tests не заменяют его.
4. Повтор Compose up/down **без `-v`** сохраняет тестовые записи, migration idempotent, fallback/backup согласован. Показаны логи без секретов, stop/restart и ограничения отсутствия HA.
5. GitHub PR CI зелёный, независимое human review, плюс свидетельство доступности релиза/GHCR при необходимости. Никакого утверждения о VPS/HTTPS/SSH.

## Отменённые предпосылки и последствия

- Не нужен ежемесячный VPS/домен/серверный SSH secret.
- Нет непрерывной доступности при закрытом ноутбуке.
- Нет публичного HTTPS для сторонних HTTP-клиентов, веб-интерфейса или webhook. **Telegram long polling продолжает обслуживать удалённых Telegram-пользователей**, когда ноутбук работает.
- Отказ от VPS — **изменение проектного решения**, а не выполненная проверка первоначального G5. Возврат к VPS требует отдельного решения и ревью; код PR #64 пока сохраняется, но не должен навязывать новые server-операции текущим исполнителям.

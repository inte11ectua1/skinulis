# AGENTS.md — правила для Codex в репозитории «Скинулись»

## Цель
Разрабатывать учебный Telegram-сервис совместных расходов на Python/FastAPI/PostgreSQL по требованиям преподавателя: https://github.com/andrey-limasov/app-conf/. Обязательные продуктовые правила в `docs/PRODUCT_RULES.md`; технические решения — в `docs/TECHNICAL_DECISIONS.md`.

## Обязательные ограничения

1. Не менять технический стек и принятые правила без явного требования в задаче/PR. Не добавлять Redis, Celery, внешние сервисы, новый язык или другую БД.
2. Python 3.12, FastAPI, Pydantic v2, SQLAlchemy **sync**, psycopg 3, Alembic, PostgreSQL 17. API-обработчики с БД — `def`, сессия на запрос, не общий глобальный Session. aiogram-бот может быть async, взаимодействует с API через httpx; у бота нет подключения к БД.
3. Деньги только целые копейки в сервисах и `BIGINT` в PostgreSQL. API передаёт денежные суммы строками с двумя знаками после точки. Запрещены `float`, `round` и округление через binary floating point.
4. Не дублировать бизнес-логику между API и ботом. Роутеры тонкие; расчёты в `services/`, pure functions по возможности.
5. Любая финансовая операция по группе атомарна, для конкурентных записей сначала lock строки группы. Существующие `confirmed` компенсации никогда не исправлять автоматически при изменении расходов.
6. Не доверять `telegram_id`, `sender_id`, `author_id`, `payer_id` из публичного JSON как доказательству полномочий. Actor только из JWT либо из проверенного bot-service запроса. Проверять членство и права на каждом защищённом endpoint.
7. Не хранить секреты в Git, тестах, логах или документации. Использовать `.env.example`, GitHub Secrets; не выдавать prod secrets в pull_request workflows.
8. Все изменения схемы — миграция Alembic + интеграционный тест. Не применять `Base.metadata.create_all` в production и не менять схему автоматически из model startup.
9. Каждый endpoint документировать Pydantic-схемами и OpenAPI-примерами; списки — с пагинацией по умолчанию 20. Ошибки по единому формату; validation error => HTTP 400.
10. Тесты обязательны для новых правил и исправленных багов, особенно split/settlement/access/concurrency. Покрытие в CI не ниже 60%. Не помечать тесты skip/xfailed, чтобы «сделать зелёным».
11. Не делать гигантских PR; одна логически завершённая задача за раз. Не удалять существующие тесты и функции без причины. Не выполнять merge в main и не изменять защиту ветки.
12. Сначала изучить `docs/PRODUCT_RULES.md`, `docs/TECHNICAL_DECISIONS.md`, относящиеся модели/схемы, потом реализовать. При конфликте — описать проблему, не принимать скрытого решения.

## Готовность задачи (Definition of Done)
- Протокол API, код и миграция (если нужна) согласованы.
- Новые unit/integration тесты написаны, в том числе негативные сценарии.
- Команды проходят: `uv sync --frozen`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy app bot`, `uv run pytest --cov=app --cov-fail-under=60` (или точные команды, закреплённые в pyproject).
- Нет секретов, простых ORM N+1, ошибок в обработке транзакций и подмены actor.
- README/OpenAPI/документация обновлены при изменении внешнего поведения.
- В ответе Codex: перечень файлов и изменений, точные выполненные проверки и результаты, ограничения/риски, что проверить вручную.

## Стиль задач для Codex
Пример: «Реализуй сервис equal split по PRODUCT_RULES.md (копейки, детерминированный порядок user_id). Добавь unit-тесты: 100.00/3, 0.01/3, пустой список, дубли, один участник. API и миграции не трогай. Запусти тесты и Ruff. Не добавляй зависимости».

## Многопользовательский процесс
Перед задачей читать `START_HERE.md`, `docs/TEAM_WORKFLOW.md`, `docs/contracts/BOUNDARIES.md`, `docs/STATUS.md`, свой SPEC и ROADMAP. Выполнять только assigned issue ID и не менять файлы чужого владельца без согласования. Не менять main, не merge, не подставлять production secrets. После каждого задания выдавать тесты, изменённые файлы, ограничения и PR link для человеческого review.

## Автозакрытие GitHub Issues (обязательно при оформлении PR)
- **Если реализация полностью покрывает Issue и приёмочные чекбоксы**, передать в описание PR реальную строку `Closes #N` (или `Fixes #N`, но предпочитать `Closes`), с точным номером **той** задачи. GitHub автоматически закроет Issue **только при merge в `main`**. Пример: полный O-07 PR — `Closes #47`, полный L-05 PR — `Closes #48`.
- **Если PR промежуточный** (mock UI, ранние тесты/документы/черновой контракт или остаётся хоть один acceptance пункт), использовать **только** `Refs #N`, **не** `Closes #N`, чтобы не закрыть задачу раньше времени. Пример: mock-only L-05 — `Refs #48`.
- Перед передачей PR на merge проверить соответствие acceptance, актуальный CI `lint/types/tests/docker-build/ci`, запросить независимый review и снять unresolved discussions. Если административный merge без approval всё-таки выполнен, открыто задокументировать исключение и **не** выдавать его за человеческий approval. `Closes` не заменяет ревью, не является командой на автоматический merge и не подтверждает G2/G3/G4 live Telegram.
- **Перед завершением каждого Codex задания** проверить описание своего PR: не оставлять `Refs` на PR с полностью готовой задачей; не оставлять `Closes` на частичном PR. Если PR уже merged с `Refs`, передать задачу руководителю для ручного закрытия после проверки; не создавать вторую пустую PR ради автозакрытия.
